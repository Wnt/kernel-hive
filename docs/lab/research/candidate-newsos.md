# Candidate: Sony NEWS-OS on a NEWS workstation (MAME `nws5000x`)

Unvalidated first pass, written under a strict 5-minute timebox. Shallow —
treat every claim below as **unverified** unless marked otherwise, and expect
this to be revised heavily before any scaffold command runs.

## What the exhibit is

Sony's NEWS (Network Engineering Workstation System) line: MIPS-based Unix
workstations from Sony Japan, running **NEWS-OS**, a BSD-derived Unix with an
X11 desktop. Visually and historically this sits next to the lab's other
1990s Unix workstations (IRIX, Solaris, Tru64, OpenVMS) but from a vendor and
market (Japanese enterprise/research) none of the current lineup represents —
that's the slot it would earn, not novelty of "another Unix box."

- The NWS-5000X's PROM/firmware ROM set, which MAME's driver requires as a

## Emulator and machine — the most important question

MAME driver: `news_r4k.cpp`, added via mainline PR #8854 (briceonk), target
system NWS-5000X (MIPS R4400, APbus expansion). Per one search result
(MAMEdev-adjacent summary, **unverified against primary source**):

- Boots **NEWS-OS 4.2.1aRD** in its current state. NEWS-OS 6 reportedly has
  boot issues (possibly async serial driver related); NetBSD only gets as
  far as the floppy installer (SPIFI driver not yet supported there).
- **"The NWS-5000X driver does not have any framebuffer emulation, so you
  must connect over the network to use the GUI."**

That last line is a potential **hard blocker** for this project's model. Every
Tier-3 host-native station captures the emulator's own framebuffer directly
(`-video none` off, streamhost reads pixels from the process). If `nws5000x`
genuinely has no framebuffer device and the GUI only exists via a remote
X/XDMCP client hitting the emulated machine over its emulated network, there
is **no local pixel surface for streamhost to capture** — the "desktop" would
have to be rendered by a second, separate X server, which is architecturally
a bridge/Tier-2-shaped problem, explicitly the thing this project is moving
*away* from, not toward. This needs primary-source confirmation
(`nws5000x-mame.md` itself, and current MAME source/whatsnew) before any
further effort — see "one experiment" below.

## Graphical target

Unknown / unverified. If framebuffer capture is not possible as described

## Pointer and keyboard

Assuming (unverified) framebuffer capture becomes possible some way: the
established pattern for the nine host-native MAME stations applies —
relative mouse via MAME's own input, keymap generated by KEYDUMP against the
driver's actual key codes, `MAME_CTL_KEY_EXCL` very likely needed (every
converted MAME station has needed it per `DEBRIDGE-CONVERSION-BRIEF.md`,
since it's a property of the ctlsock keyboard-matrix serialization, not of
any one guest). Nothing NEWS-specific checked here.

## Host-native capture plan

Would follow Tier 3 exactly as documented in
`docs/lab/DEBRIDGE-CONVERSION-BRIEF.md`: `stations/mame-native/x11-runtime.sh`,
a `native.d` build stanza, KEYDUMP-generated keymap, `SAVEST golden` for the
checkpoint — **contingent on `MACHINE_SUPPORTS_SAVE` being set for the
`news_r4k` driver**, which was not checked in this pass. If save states
aren't supported, there is no golden checkpoint and every session starts
from cold boot — a separate, serious viability question from the framebuffer
one above.

## Effort, risk, open questions

Very high uncertainty, more open questions than answers:

- Does `nws5000x` actually expose a capturable framebuffer, or is the GUI
  genuinely network-client-only? (**the** blocking question — see below)
- Where does install media for NEWS-OS 4.2.1 actually come from, hashed and
  archival, not community-forum links?
- Where does the NWS-5000X PROM/ROM set come from?
- Does the driver support MAME save states (`MACHINE_SUPPORTS_SAVE`)?
- Is 4.2.1aRD graphical at all locally, or console-only with X available
  solely to remote clients?
- Driver is very recent (added via a 2020s-era PR per the search hit) —
  likely still rough; check MAME changelog/whatsnew for post-merge fixes.

**One experiment that resolves the most uncertainty fastest:** read
`briceonk/news-os`'s `nws5000x-mame.md` in full (primary source, not a search
snippet) and, if still ambiguous, boot the driver in scratch MAME on CT950
with `-video none` and outside network, and simply check whether anything
appears on the emulated framebuffer at all. If the doc or that five-minute
boot confirms "GUI is remote-client-only," this candidate is very likely
**not viable as Tier 3** in its current driver state and should be shelved
pending upstream MAME framebuffer support, not pursued as a bridge.

## VOM hints (reference only, added 2026-08-17)

The Virtual OS Museum collection on this box ships a working installation of
this OS. **We take no media from it** — see the media rule in
[`AGENTS.md`](../../../AGENTS.md); it is a recipe reference only. These hints were read from its *package metadata* (dpkg file
lists on the host rootfs), which names the emulator, the ROM/firmware files and
the author's own screenshots — the screenshot filenames are effectively his
verdict on what the install actually reaches. The boot scripts themselves live
on the 173 GB guest-image disk, which has NOT been extracted, so the exact
command lines below are inferred from filenames, not read.

**VOM install:** `newsmips/.../news_os_4.2.1ard_config/` — and its file list
**corroborates the framebuffer blocker recorded above, while also showing the
author's way around it.**

- MAME shape confirmed: `news_os_4.2.1ard.chd`, `nvram/nws5000x/`, `roms/`.
- **But it also ships `run_x11`, `xdmcp.py`, and a `fonts/sony/` tree.** The
  clear reading: the GUI is not painted into a local framebuffer at all — the
  guest is driven to an **X server over XDMCP**, with Sony's own fonts supplied
  host-side so the session renders correctly. The screenshots
  (`00_Login_Window.png`, `01_Desktop_Applications.png`) are of that X session.
- **This reframes the candidate rather than killing it.** Our converted MAME
  stations already run **Xvfb + emulator, host-native** (`x11-runtime.sh`, as
  `tru64` does). An Xvfb hosting an XDMCP session from NEWS-OS is still
  host-native capture — no Debian kiosk guest required. What changes is the
  input path: keys and pointer would go to the X server (XTEST), not through
  `mamesock`/ctlsock, so none of the keymap/`MAME_CTL_KEY_EXCL` machinery
  applies and a new input plane would be needed.
- Also note the exhibit would then be "NEWS-OS's desktop displayed on our X
  server", which is a caption-honesty question worth settling before building.
