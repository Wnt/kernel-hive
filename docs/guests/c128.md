# Commodore 128 (PAL, 80-column) — gallery station notes (udp/54087)

**Guest:** a captured **Debian 13 (trixie) x86_64 kiosk** running **VICE `x128`**,
emulating a **PAL Commodore 128** in its native **80-column** mode, resting at
the machine's own untouched power-on screen with the **CP/M 3.0 system disk in
drive 8, unbooted**. A **kiosk** — streamhost captures the
Linux framebuffer + AC97 audio exactly like every other station. See
**`streamhost/docs/BRIDGE.md`**.

**Shared base:** `/data/vms/bridge/bridge-base-trixie.qcow2` — already contains the
whole VICE family, including `x128` and the complete `C128` ROM tree.
**Build script (station):** `scripts/build-guests/tiles/c128.sh` — thin overlay + kiosk
`launch.sh` + the deferred-attach helper + ROM repair + CP/M media staging +
quiet console + checkpoint capture + two framebuffer-asserted post-capture proofs, fully
automated and idempotent, ~3 minutes.
**Station dir (host):** `/data/vms/streamhost/tiles/c128/`.
**Registry entry:** `registry/tiles/c128.json` (slot 87, udp 54087, VMID 223,
ssh hostfwd 127.0.0.1:5823).

## Why this machine is here

The C128 is three computers in one case. Native C128 mode drives the **VDC**, a
second video chip with 80-column RGBI text and its own 64 KB of video RAM. C64
mode is a real Commodore 64, not an emulation. And a second CPU, a **Zilog
Z80A**, runs **CP/M Plus (3.0)** — the operating system that ran business
computing before MS-DOS, and the one story no other exhibit in this lineup can
tell.

## Media and license

Almost everything is in the box already. VICE bundles the C128 ROMs — BASIC
lo/hi, the KERNAL, the editor, the Z80 BIOS, the character generator and the
C64-mode pair — so the machine itself needs no external media.

The **CP/M system disk** does not ship with VICE, because it is ordinary
distributed media rather than a ROM. It is fetched once, hash-pinned twice, and
staged **inside the guest** at `/opt/bridge/media/c128/cpm.d64` (the same
in-guest media convention `c64.sh` and `amiga.sh` use). The bits are never
committed — only the URL, the hashes and the licence class.

| item | detail |
|---|---|
| source | `https://www.zimmers.net/anonftp/pub/cbm/demodisks/c128/cpm.system.6228151676.d64.gz` |
| `.gz` sha256 | `6ed0da2d8a6fa74ae7b6e6cb67d78e1806a2a625ca839b4d93558c5ce7f44cb9` (76 230 B) |
| `.d64` sha256 | `69159226bf1996d8fc8c8921f094cd03955c7a8b9ecf800069d1c369dc6e5a1d` (174 848 B) |
| class | **preservation-source** — Commodore-era CP/M, redistribution terms unclear |

Both hashes are verified on the host at intake **and again inside the guest
after transfer**, and the file size is asserted to be a 35-track `.d64`.

- **VICE 3.9** — GPLv2; bundles the C128/C64 ROMs for emulation use.

## The scene, and how a visitor drives it

The checkpoint is **the machine's own untouched 80-column power-on screen**, in the
VDC's cyan on black:

```
        COMMODORE BASIC V7.0 122365 BYTES FREE
         (C)1986 COMMODORE ELECTRONICS, LTD.
              (C)1977 MICROSOFT CORP.
                ALL RIGHTS RESERVED
READY.
```

Nothing is curated and nothing is typed into it. This is the **plus4 lesson**
applied before the mistake rather than after it: an earlier Plus/4 checkpoint rested
inside its ROM office suite and had to be recaptured, because a visitor arrived in
the middle of an application with no idea what it was or how to leave. The
affordances belong in the exhibit UI, around a state the machine itself chose.

| Step | Keys | Result |
|---|---|---|
| Boot CP/M | `BOOT` then `RETURN` | `CP/M 3.0 On the Commodore 128 / 80 column display / A>` |
| Back to BASIC | the gallery's **Reset** | `loadvm golden` — the power-on screen again |

The UI's `c128` on-screen keyboard puts `BOOT`+`RETURN` on a single **CP/M**
button, because the interesting thing about this machine should not depend on
knowing a BASIC 7.0 keyword.

**CP/M is slow to boot, and that is the machine.** CP/M Plus loads its BIOS and
BDOS off the disk through an emulated 1541 at 1541 speed: **~85 s** on a cold
run, ~30 s once the host page cache is warm. The screen narrates it
(`BOOTING CP/M PLUS`, the module table, `59K TPA`), so it does not read as a
hang.

**CP/M is a one-way trip.** There is no supported route from the CP/M prompt
back to BASIC without resetting the machine, and a reset with the CP/M disk in
the drive simply boots CP/M again. The gallery's Reset restores the checkpoint,
which is the way back.

### Why there is no C64 button

`GO64` `RETURN` `Y` `RETURN` works — and it is **invisible**. C64 mode paints
the VIC-II, but with `-80col` the visible canvas is the VDC, and C64 mode stops
updating it. Measured after the capture (2026-08-09): two screendumps **10 s apart
were byte-identical**, while the control — the live BASIC prompt over the same
interval — alternates between exactly two hashes as the cursor blinks. So the
frozen frame is the VDC going dead, not a keystroke that missed. A C64 button
would hand the visitor a dead screen with no way back, so it is not shipped.
The sequence is fine; the display is not.

## Device set and launcher

Identical in shape to its kiosk siblings (`c64`, `vic20`, `plus4`, `apple2`,
`atarist`, `amiga`, `mpf2`) — see `streamhost/tiles/c128/qemu-streamhost.sh` —
except for **768 MB of RAM instead of 1536** (below). The kiosk launcher is:

```
x128 -sounddev alsa -pal -80col -remotemonitor
```

on an **800×600** X root.

### `-80col`, and the two flags that are traps

In VICE's SDL2 build the VDC output is a **second canvas**. `-dualwindow` and
`+hidevdcwindow` do not help: with no window manager in the kiosk the second
window never becomes visible, and a capture taken with either shows only the
VIC-II. `-80col` sets `C128ColumnKey=0`, which makes the VDC the **active**
canvas; with DualWindow off (the default) every canvas shares one SDL container,
so there is a single X window showing 80 columns. The same flag also selects
which display the machine **boots** into, so one flag sets both the idle screen
and the visible chip.

### Window vs X root — measured, not assumed

There is no window manager, so an SDL window larger than the X root is silently
clipped and mispositioned. `xwininfo` in the guest, 2026-08-09:

| invocation | window | on a 1024×768 root | on a 1920×1080 root |
|---|---|---|---|
| `-80col -VDCdsize` | 1578×1152 at +171,−36 | badly clipped | **still clipped** (1152 > 1080) and ~45 % of the root is black |
| `-80col` (no doubling) | 789×576 | — | — |

So the station drops the doubling flag and keeps the **800×600** root its VICE
siblings use: 789×576 fills it edge to edge, and every VDC pixel is 1:1
(80 columns × 8 px = 640 px of text plus border), which is what makes
80-column text crisp rather than resampled. Doubling would have cost a 1600×1200
capture — four times the pixels of any other kiosk — to gain nothing.

### Why the CP/M disk is not on the command line

The C128 KERNAL reads the boot sector of drive 8 **at every reset**, so a CP/M
disk present at power-on **autoboots**. That is not a theory: the first recon
launch used `-8 <d64>` and the station came up mid-way through `BOOTING CP/M PLUS`
and never showed BASIC at all.

Instead `/etc/bridge/launch.sh` backgrounds
`/usr/local/bin/c128-attach-cpm.sh`, which waits for VICE's text monitor to
start listening on guest-local `127.0.0.1:6510`, waits **10 s more**, and then
issues `attach "<d64>" 8` followed by `x` (resume). The wait is anchored to
VICE's own readiness rather than to the shell's start, so a slow emulator start
cannot race the attach in front of the reset. Cold boot and `loadvm golden`
therefore reach the same state.

Two build-time traps are worth recording:

- The helper's log lives in **`/tmp`, not `/run`**. The kiosk session runs as the
  unprivileged `bridge` user and `/run` is root-owned, so the first version
  attached the disk correctly and then died on the redirect — and the build
  reported failure for a run that had succeeded. A proof channel the prover
  cannot write to is worse than no proof channel.
- The build **polls** for that log instead of checking once. `/tmp` is emptied by
  the cold boot the capture starts from, and the attach lands ~10 s behind VICE; a
  single `grep` lost that race on the first run by about one second.

### The other two inherited traps

- **VICE 3.9 segfaults whenever its stdout is not a terminal** —
  `vice_banner()` → `strlen(NULL)` — and prints nothing at all, so the kiosk
  profile must not redirect `startx`'s output to a file. Backtrace and symptom in
  [`vic20.md`](vic20.md).
- **VICE's `make install` skips ROM data files.** `c128.sh` repairs the `C128`
  and `DRIVES` trees from the retained source tree and **asserts** every ROM the
  machine needs: BASIC lo/hi, KERNAL, chargen, the C64-mode pair (`GO64` uses
  them) and the 1541/1571 drive ROMs (CP/M boots through one). On this frozen
  base the C128 tree happens to already be complete — the assertion is what
  proves that, and it is exactly the assertion the C64 and VIC-20 adds wished
  they had had.

## Memory

**768 MB**, half what `vic20`/`plus4` use, and verified rather than assumed. With
`x128` running at the scene the guest reports **MemAvailable 387 MB of 708 MB**
(`x128` RSS ~178 MB). The build asserts `MemAvailable > 200 MB` and fails
loudly if a future VICE grows past it. Host-side, the station's QEMU sits at
**~688 MiB RSS** (704 316 kB, measured on the live service).

## Keyboard pacing

`SH_KEY_MIN_HOLD_MS=80`, `SH_KEY_MIN_GAP_MS=80` — four PAL frames each way.
**Carried over from the VIC-20's bisect rather than re-measured**: same
emulator, same 50 Hz frame, same host, and the failure those numbers guard
against is a host scheduling stall rather than a property of the emulated
machine (`scripts/dev/emu-key-pacing-bisect.py`: 40/40 corrupted 1 line in 22,
80/80 none in 22 — see [`vic20.md`](vic20.md)). The playbook's two-frame figure
is a floor, not an answer. Re-bisect if this station ever drops characters.

No `demoProgram`: the interaction here is CP/M, not a BASIC type-in.

The readiness and proof predicates are **colour** predicates, because colour is
what separates the three states on this machine: native BASIC is **cyan**
(3651–3964 pixels of it on the scene), CP/M Plus is **magenta** (2003 pixels,
zero cyan), and a bare X root, a dead `x128` or the Linux console (grey text)
score zero cyan. Requiring `magenta < 100` in the ready test is what stops
"ready" from accepting a machine that has autobooted CP/M — the exact failure
this station hit first time out.

## Cold boot and rollback

Zero input is genuine, and a cold boot reaches the scene: the machine's ROM
comes up unattended at BASIC 7.0 and the CP/M disk is attached silently ~10 s
later without touching the screen. See
`scripts/coldboot/c128-zero-input-prep.md`.

To withdraw the station: `systemctl stop streamhost@c128`, set `enabled: false`,
regenerate, republish the three runtime documents (tiles.json, gallery-manifest.json AND golden-manifest.json — the third is the reset allow-list). To rebuild:
`scripts/build-guests/tiles/c128.sh --force`, which replaces `overlay.qcow2` and so
**destroys the checkpoint inside it**, then captures and re-proves a new one.
