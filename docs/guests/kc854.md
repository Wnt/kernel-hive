# KC 85/4 (CAOS 4.2) — gallery tile notes (udp/54132)

**Guest:** a captured **Debian 12 x86_64 kiosk** running a purpose-built
**MAME 0.289 `kc85_4`**, emulating the **KC 85/4** that VEB Mikroelektronik
"Wilhelm Pieck" Mühlhausen shipped in 1988. An **"emulator bridge"** tile —
streamhost captures the Linux framebuffer + AC97 audio exactly like every other
tile. See **`streamhost/docs/BRIDGE.md`**.

**Shared base:** `/data/vms/bridge/bridge-base.qcow2` (read-only backing; built
by `scripts/build-guests/bridge-base.sh`).
**Build script (tile):** `scripts/build-guests/kc854.sh` — thin overlay,
SDL/X11 runtime, SHA1-assembled romset, kiosk `launch.sh`, quiet console,
golden bake, framebuffer + keyboard proof; fully automated, `--force` rebuilds.
**Build script (emulator):** `scripts/build-guests/build-mame-kc854.sh`.
**Tile dir (host):** `/data/vms/streamhost/tiles/kc854/` — `overlay.qcow2`
(thin, on the shared base; holds the INTERNAL `golden` snapshot),
`qemu-streamhost.sh`, `tile.env`, `evidence/`.
**Registry entry:** `registry/tiles/kc854.json` (slot 132, udp 54132, VMID 235,
ssh hostfwd 127.0.0.1:5835).

## The machine, and the naming trap on the placard

U880 (East Germany's unlicensed Z80 clone) at **1 773 447 Hz** — MAME's
`KC85_4_CLOCK`, `src/mame/ddr/kc.h` — 64 KB of main RAM plus 64 KB of dedicated
screen memory, **320×256 at 50.080411 Hz**, two module slots and an expansion
connector, and CAOS 4.2 in ROM.

**The KC 85 line from Mühlhausen and Robotron's Z9001 / KC 85/1 / KC 87 are
different, incompatible machines.** The GDR renamed products under a common
*Kleincomputer* label, so Mühlhausen's HC 900 became the KC 85/2 while
Robotron's Z9001 became the KC 85/1. Robotron's Z1013 and A5105 belong to that
other family; the recon for this add judged both to be placard coverage rather
than separate tiles, so the GDR family is folded into
`registry/posters/kc854.md`.

## Media and license

One staged input: the merged MAME romset zip `kc85_2.zip` (sha256
`ed5b8a56…`), recorded in `docs/lab/ASSETS-MANIFEST.md` with a
`check-assets.sh` row. The bits are never committed and never served.

**The romset is assembled BY SHA1, never by filename.** `mame -listxml kc85_4`
wants five ROMs; one of them, `basic_c0.854` (sha1 `c2e3af55…`), does not exist
under that name anywhere in the merged archive — the byte-identical dump is
stored as `kc85_3/basic_c0.853`. Measured 2026-08-09 by indexing all 18 members
of the zip. A filename-driven assembly produces a set with no BASIC in it and no
error. The builder therefore indexes members by SHA1, takes the wanted (name,
sha1) pairs from the **shipping binary's own** `-listxml`, and emits a fresh
`kc85_4.zip`.

**`-verifyroms` is not the gate.** kc85_4 is BIOS-selectable (`caos42` /
`caos41`), so verifyroms objects to whichever alternative BIOS is absent even
when the shipped set is hash-perfect. The builder asserts the SHA1 of the three
ROMs the tile actually pins and prints verifyroms as advisory output.

## Emulator provenance

MAME **0.289** (tag `mame0289`, commit `d0b7160e…` — the newest upstream
release), built as `SUBTARGET=kc85 SOURCES=src/mame/ddr/kc.cpp` in the Bookworm
chroot whose glibc/libstdc++ match the Debian 12 bridge. The lab host's packaged
MAME is 0.276 and links against Debian 13; bookworm's own package is 0.251, the
release in which `kc85_4` is still a clone of `kc85_2` with a different ROM
split. Pinning one binary and assembling the set against **that** binary's
`-listxml` is the only way the two can be known to agree.

The build applies `mame-irix-skip-warnings.patch`, the same one-line patch the
mpf2 tile ships.

## The red nag screen

`mame -listxml kc85_4` reports `<driver status="preliminary">`. Stock MAME opens
such a driver with a full-screen red **"THIS SYSTEM DOESN'T WORK"** panel that
`-skip_gameinfo` does **not** suppress and that a headless `-video none` probe
never renders — so a build script can pass while the exhibit is an error message
for ever. The patched binary makes `ui.ini`'s `skip_warnings 1` apply to that
panel, so the kiosk posts no dismissal key and the golden is a genuinely
untouched boot screen. The builder's `wait_for_caos()` asserts the panel's own
red is absent from the frame, so a regression fails the build.

## Acceptance criteria

- **Ready framebuffer:** CAOS 4.2's own power-on screen — its command menu and
  prompt — drawn fullscreen with aspect correction on the bridge base's stock
  **1024×768** X root. No Linux console, no X log, no pointer, no red panel.
- **Reset mode:** `loadvm`, internal snapshot `golden`. No post-restore keys.
- **Pointer:** none. `--pointer none --input-backend disabled`; X runs with
  `-nocursor`. The KC's pointing options were a light pen and a joystick module,
  neither of which this tile streams.
- **Keyboard:** PS/2 only, paced (see below).
- **Login:** none. `credentialsRef` is `guest/kc854` for form only; the guest
  Debian kiosk is reached with the shared bridge key.

## X root and emulator window

320×256 is the machine's **pixel** count, not the picture's shape: a KC 85/4
drew a 4:3 image on a television. `-resolution` is therefore **not** forced to
320×256 — the mpf2 add proved what that costs (a narrow strip in a black root).
MAME runs `-nowindow` (fullscreen) with `-keepaspect -prescale 2 -video soft
-nofilter` on the stock 1024×768 root, which reconstructs the 4:3 picture and
fills the captured frame. Any change to the launcher or the X geometry
invalidates the golden; re-bake it.

`-bios caos42` is pinned explicitly rather than left to the driver default: the
default is a property of the MAME revision, and a silent flip to CAOS 4.1 would
change the exhibit's boot screen without changing anything in this repo.

## Keyboard: a German layout, derived mechanically

`registry/tiles/kc854.json`'s `keyboard.charMap` was **derived from the driver
source, not measured experimentally** — `scripts/dev/mame-keymap.py --file
src/mame/ddr/kc_keyb.cpp`, the same tool and method the MPF-II remaps came from.
MAME declares each matrix key as a `PORT_CODE` (the host key that drives it)
plus its `PORT_CHAR`s (what the guest produces unshifted and shifted), which
gives the translation exactly.

Two families of difference came out of it:

- **The plain letter row is UPPER case.** Every letter is declared
  `PORT_CHAR('B') PORT_CHAR('b')`, in that order, so shift gives **lower** case
  — the opposite of every later convention. Unshifted `basic` produces `BASIC`.
- **The punctuation is German.** `:` is on the host `-` key, `+` on `;`, `-` on
  `=`, `^` on `[`, and the shifted number row is Continental: Shift+2 is `"`,
  Shift+6 `&`, Shift+7 `'`, Shift+0 `@`. Untranslated, a BASIC listing loses or
  misplaces most of its punctuation.

The map is expressed entirely as `charMap` entries — including the 52 letter
entries — rather than as `keyboard.letterCase`. `letterCase: "upper-only"` means
*the machine has no lower case and its shifted letter row is symbols*, which is
true of the MPF-II and the PETs and is **not** true here. Spelling the inversion
out in `charMap` is honest, is what the derivation tool emits, and has the
practical advantage that `labctl` gets it right too — `labctl` reads
`SH_KEY_MAP` and knows nothing about `letterCase`.

### A shared-code bug this tile is the first to hit

`SH_KEY_MAP` is `guest:host` pairs joined by commas, so a guest character that
*is* a colon rendered as `::-`, and `labctl`'s `split(':', 1)` read that as an
empty guest and **dropped it silently**. A German keyboard puts `:` on the host
`-` key, so this tile needs it. Fixed at the right level rather than worked
around: `render_key_map()` in `scripts/tiles-registry.py` percent-encodes
exactly `%`, `,` and `:`, and `keymap_unescape()` in `scripts/labctl` decodes
them. Nothing else is touched, so mpf2's existing `=:O,-:I,+:P,(:*,):(,*:)`
renders byte-identically.

## Key pacing

MAME samples the emulated keyboard matrix once per emulated frame; at
50.080411 Hz that is **19.97 ms**, so the frame-derived floor is 40/40. The
VIC-20 add showed that floor is not sufficient on this box, so the shipped
values were **bisected** rather than derived —
`scripts/dev/emu-key-pacing-bisect.py` on a namespaced clone, 2026-08-09, a
32-character line typed at the CAOS prompt, 12 trials per pacing:

| hold / gap | lines corrupted |
|---|---|
| 40/40 | 1 of 12 (`K` and `O` dropped out of `KLMNOPQRST`) |
| 60/60 | 1 of 12 |
| **80/80** | **0 of 12** — shipped |
| 250/250 | 1 of 1 — **seven** characters lost |

**250/250 is not a safe upper bound on this machine, and that broke the
tool.** `emu-key-pacing-bisect.py` captures its reference at 250/250 on the
assumption that a long hold cannot lose anything. On the KC it lost seven of 32
characters — the line stopped at `…KL` — so the reference was the outlier and
every fast trial agreed with every other. Taken at face value the tool reports
`12/12 corrupted` at all three pacings; the table above re-scores each frame
against the consensus frame, whose 32 characters were read off the framebuffer
one by one. The KC 85 keyboard is a **separate serial device with its own
repeat timing**, not a matrix the CPU scans, so holding a key longer is a
different failure rather than a conservative one. The tool's docstring now says
so.

A second, unrelated instrument bug turned up in the builder: a proof that opened
a fresh QMP connection per key dropped the `a` out of `basic`, while a
single-connection run at the same 80/80 lost nothing in 12 trials. The builder's
`type_paced` therefore holds one connection open, which is also what streamhost
itself does.

## Golden

`resetMode: loadvm`, internal snapshot `golden`, no post-restore keys. **The
fixture is the machine's own untouched power-on screen** — CAOS 4.2's command
menu, which is simultaneously the KC's honest idle state and its own launcher,
because the operating system prints the list of things you can type. Nothing is
typed before the bake. The two prior lessons this obeys: the mpf2 golden was
baked over its own verification output and had to be re-done, and the Plus/4's
first golden rested inside an application and dropped visitors into the middle
of it with no idea how to leave.

The builder's keyboard proof runs **after** the bake, against the restored
fixture, and then restores again — so nothing it types can reach the golden.

## Memory

`--mem 768`, verified on the live tile: guest `MemTotal` 725 456 kB,
`MemAvailable` **410 976 kB** with X and MAME running, and host QEMU
`VmRSS` 739 072 kB. The guest runs one Z80 emulator under X and nothing else,
so 768 MB is roughly half again what it needs and the tile costs the box less
than half of a 1536 MB bridge sibling.

## Rollback

Keep `overlay.qcow2` (it *contains* the golden) and the launcher as an atomic
pair. To rebuild: `scripts/build-guests/kc854.sh --force`, which stops only this
tile and refuses to run while `streamhost@kc854` is active. The emulator binary
and the staged romset are outside the overlay, so a rebuild does not re-download
or re-compile anything.
