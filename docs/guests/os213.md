# os213 — Microsoft OS/2 1.30.1, Presentation Manager

IBM OS/2 1.3 (1990; Presentation Manager itself debuted in OS/2 1.1, 1988) —
the last operating system IBM and Microsoft shipped together, six months
before Windows 3.0 ended the partnership. This station runs the Desktop
Manager shell of OS/2 1.x, the predecessor to the Workplace Shell that
arrived with OS/2 2.x/Warp. It sits beside `nt351` and `os2warp` as a third
point in the museum's IBM/Microsoft desktop lineage, at the 16-bit
protected-mode end of it.

## Install recipe

The station installs from the 10-floppy IBM Standard Edition set (`Install`,
`Disk01`-`Disk05`, `Driver1`-`Driver4`) onto a FAT hard disk, under 16 MB RAM
on an ISA machine with no PCI bus. Media is swapped over QMP
`blockdev-change-medium` on the `fd0` backend during install; the daemon
waits on framebuffer proof (`fb-wait.py --change`/`--settle`), never a
relaunch per disk or a guessed sleep.

## Device set

```text
qemu-system-i386 -name streamhost-os213 \
  -enable-kvm -m 16 -smp 1 \
  -machine isapc -cpu 486 \
  -rtc base=localtime \
  -boot c \
  -device isa-cirrus-vga \
  -display dbus,p2p=on,audiodev=snd0 \
  -audiodev dbus,id=snd0,out.frequency=48000,out.channels=2,out.format=s16 \
  -device sb16,audiodev=snd0 \
  -drive file=os213-golden.qcow2,format=qcow2,if=none,id=hd0 \
  -device ide-hd,drive=hd0,bus=ide.0,unit=0 \
  -qmp unix:qmp.sock,server=on,wait=off
```

- `-machine isapc -cpu 486`: OS/2 1.x predates PCI entirely. A
  `pc-i440fx-11.0` machine freezes this guest at SeaBIOS's "Booting from Hard
  Disk...", well before the OS/2 banner. The station runs under KVM: QEMU
  TCG traps this guest right after its boot banner (docs/lab/OS213-WAVE.md
  Wall 3).
- `-m 16`: 16 MB is the working point; `-m 8` also froze at the same SeaBIOS
  stage in the race.
- Disk geometry is left to QEMU's auto-detection on `-device ide-hd`. No
  `cyls=`/`heads=`/`secs=` anywhere — see Traps.
- `-device isa-cirrus-vga`: Presentation Manager runs its plain VGA driver at
  640x480x16. Never `isa-vga` — see Traps.
- Pointer: `qemu-ps2-relative` — see below.
- No `-net`/`-netdev` line at all: OS/2 1.3 ships no TCP/IP stack.

## Pointer

PS/2 relative only: `-machine isapc` has no USB bus, so `usb-tablet` — and
with it every USB absolute route the fleet otherwise uses — is unavailable
here. This is the machine's only transport, not a shortcut.

**The guest's mouse stack is present and complete.** Read out of the disk
image (`CONFIG.SYS`, verbatim):

```text
DEVICE=C:\OS2\POINTDD.SYS
DEVICE=C:\OS2\MSPS201.SYS
DEVICE=C:\OS2\MOUSE.SYS TYPE=MSPS2$
DEVICE=C:\OS2\PMDD.SYS
```

`MSPS201.SYS` is the Microsoft PS/2 mouse device driver and `MOUSE.SYS
TYPE=MSPS2$` binds to it; `POINTDD.SYS` + `PMDD.SYS` are the pointer-draw
pair Presentation Manager draws the sprite with. The earlier "maybe this
pre-installed image has no mouse driver" lead is **disproven** — do not
re-run it.

**Clicks work.** The 2026-09-13 `changed=0` click result was an aiming
failure in the test harness, not a guest fault. Measured on a rig clone
(`fb-react`-style masked pixel diff of QMP `screendump` frames):

| Step | Result |
|---|---|
| single left click on a Group-Main item (QMP `input-send-event` `btn`) | changed=**3631**, bbox 256,171-479,332 — the selection moved |
| double click on the same item | changed=**94050**, bbox 56,56-559,375 — **OS/2 System Editor opened** |

Both `input-send-event` `btn` and HMP `mouse_button 1` / `0` deliver the
button; nothing about the button path was ever broken.

### The 2:1 mickey ratio — why aiming failed, and why one scale cannot fix it

OS/2 1.3's mouse driver uses the classic **2:1 horizontal:vertical mickey
ratio**. Measured from a homed pointer with single-unit `rel` events,
0.004 s apart, on the station's own device set:

| Sweep | Units sent | Pixels moved | Gain |
|---|---|---|---|
| 50 x `rel x=+1` | 50 | 51 | **1.02 px/unit** |
| 50 x `rel y=+1` | 50 | 25 | **0.50 px/unit** |
| 20 x `rel x=+10` | 200 | 177 | 0.885 px/unit (the driver's acceleration curve bends above ~1 unit/event) |
| 20 x `rel y=+10` | 200 | 100 | 0.50 px/unit |

So a commanded position derived from relative deltas lands at roughly
**twice** the intended vertical distance from where the harness thought the
pointer was — far enough that every click in the first bake fell on empty
desktop. Aim with single-unit events and halve the y count and the clicks
land.

This is also why `SH_CURSOR_SCALE` cannot linearise this station: the daemon
exposes **one** scalar (`streamhost/src/config/mod.rs`), and this guest needs
x=1.0 with y=0.5. Setting either value breaks the other axis. The station is
therefore left at `SH_CURSOR_SCALE=1.0` (the default) and the route to a real
1:1 pointer is absolute, not a rescaled relative one.

### Absolute via `kh-ramabs` — `0x253ca`, `point16le_yx` — CUT OVER 2026-09-13

**Status 2026-09-13: LIVE.** Layout row landed in `0007`, `/opt/qemu-os213`
built, golden cold re-baked under it, address re-derived (unchanged at
`0x253ca`) and re-swept. Launcher and registry updated; see ROLLBACK.md for
the binary+golden+launcher unit and the one-line fallback to relative.

The guest keeps the Presentation Manager pointer as an **int16 pair in
Y-THEN-X order, little-endian, top-left origin**, at guest-physical
**`0x253ca`** on the `os213-ptr/ramabs` golden (y at `0x253ca`, x at
`0x253cc`). **`0007`'s layout table does not yet carry this combination.** It has
`macpoint16be` (y-first but BIG-endian), `point32le_yx` (y-first but int32)
and `point16le_yup_yx` (y-first but y counted UP) — nothing that is int16,
little-endian, y-first and y-DOWN. It is a **one-row addition** to
`kh_layouts[]` in `streamhost/qemu-patches/0007-kh-ramabs-guest-ram-absolute-pointer.patch`,
the table having landed with oberon:

```c
{ "point16le_yx",     KH_LAYOUT_POINT16LE_YX,     2, false, true,  false },
```

plus its enumerator and its mention in the `unknown layout=` error. This
session proved the address with an equivalent hand-added layout on a private
build; the row above is what to land.

Measured on the CUTOVER golden (re-baked under `/opt/qemu-os213`, address
re-derived and unchanged), `-loadvm golden`, ten `MOVEA`s over five targets in
two laps:

| commanded | device sensor (`STAT pos=`) | framebuffer (naive locator) |
|---|---|---|
| 20,20 | 20,20 | 12,14 — locator artifact, see below |
| 619,20 | 619,20 | 619,20 |
| 20,459 | 20,459 | 20,459 |
| 320,240 | 320,240 | 600,460 — park-blob artifact, see below |
| 619,459 | 619,459 | 619,459 |

Both laps identical, `converged=22 gaveup=0 probefail=0 refused=2`. The
sensor is the guest's own variable read back, so sensor-exact 10/10 means the
guest really holds the commanded pixel on every target, both laps. The naive
locator misses two of the ten frames for reasons that are diagnosed, not real
pointer error: `20,20` is the same locator artifact recorded below (XOR
sprite, diff blob swallows window chrome, bbox lands 8,6 up-left of the arrow
tip), and `320,240` this run picked up the PARK position (600,460, where the
harness moves the pointer between targets) because the naive locator's blob
score at the park frame dominated — a harness sequencing artifact, not the
address failing. **Proof of the actual pixel is the sensor readback**, which
is exact on both. A left click at the commanded pixel `235,211` (the
Group-Main "OS/2 Window" icon) selected it: `changed=3542 bbox
256,205-479,254` (`scripts/dev/fb-react.py`), confirming absolute positioning
AND the click land on the same coordinate system.

#### The three addresses that pass the write probe, and the two that lie

The connect-time probe is **necessary but not sufficient on this guest** —
this is new, and it contradicts `docs/lab/BEOS-ABSOLUTE-POINTER.md` §3's "if
more than one verifies, stop and escalate" only in the sense that here the tie
IS breakable, by the sweep:

| address | layout | probe | `MOVEA` sweep |
|---|---|---|---|
| `0x19514` | `point16le` | FAILED | — read-only copy (MOU top-left-origin) |
| `0x10fe20`, `0x10fe24` | `point16le` | FAILED | — read-only copies |
| `0x10c624` | `point16le_yup` | FAILED | — PM bottom-left-origin copy |
| `0x24ea0` | `point16le_yx` | **passed** | `converged=0 gaveup=21` — **does not move the pointer** |
| `0x24eb0` | `point16le_yx` | **passed** | untested |
| **`0x253ca`** | `point16le_yx` | **passed** | **`converged=21 gaveup=0`, sensor exact 10/10** |

So a probe pass alone would have shipped `0x24ea0`, which steers nothing.
**Always finish with a MOVEA sweep and read `converged`/`gaveup`.**

#### Why the failed candidates fail, readably

Every FAILED row walks the same way: after eight probe tries the guest holds
`313,243` when the device wanted `320,239` — x drifting **-1 per try** and y
**+0.5 per try**. That is the 2:1 mickey ratio applied to the probe's own
1-unit diagonal nudge, with the device's write ignored. A read-only copy
therefore announces itself here by drifting at exactly the station's measured
relative gain.

#### How the address was found (the one-stage bias search returns ZERO here)

`scripts/dev/os213-ramabs-scan.py`, two stages, because the XOR sprite defeats
the locator — see that file's header and `docs/lab/OS213-WAVE.md`. Short
version: only ~2000 of 8.4M int16 slots change while the pointer moves, so
read the pointer's true positions out of RAM first, then run the exact-bias
family search against those instead of against located pixels.

**Re-derive after every re-bake** (proven 2026-09-13 against the cutover
bake — the address was unchanged at `0x253ca` but MUST be re-checked, not
assumed, since it is bound to the exact bake). Commands, verbatim, from
labhost (`derive2.py`'s own one-stage family search returns zero here — that
is expected, see wall 1 above; `gm*.bin` is what the two-stage scan reads):

```sh
ssh lab 'cd /data/vms/sandbox/os213-ptr/ramabs && python3 derive2.py'   # relaunches the rig, leaves gm0..gm5.bin
ssh lab 'python3 /data/vms/sandbox/os213-ptr/repo/scripts/dev/os213-ramabs-scan.py scan /data/vms/sandbox/os213-ptr/ramabs 6'
# inspect the printed slots for the known offset (or a new one if the bake moved it), then:
ssh lab 'QEMU_BIN=/opt/qemu-os213/bin/qemu-system-x86_64 python3 /tmp/ramsweep.py 0x253ca point16le_yx c'
# read converged/gaveup in the STATend line -- converged>0 gaveup=0 is the bar.
```

`derive2.py`'s `RELAUNCH=1` default re-launches the rig with `$QEMU_BIN`
inherited from the shell that invokes it — export `QEMU_BIN` in the same
`ssh lab '...'` command, not a prior one, or it silently falls back to
`/opt/qemu-beos` (harmless for the scan step, since it only reads raw guest
RAM and never arms `-device kh-ramabs`, but wrong for the sweep step, which
does).

## Network

None, deliberately. OS/2 1.3 ships no bundled TCP/IP stack (IBM TCP/IP for
OS/2 1.3 was a separate product IBM sold on its own), so os213 is off the
retronet: it has no `rn-tapnet.sh`, and per AGENTS.md rule 15 none is

## Sandbox verdict

os213 is an emulated machine under the fleet QEMU, not a host application —
the visitor's reach ends at the emulated i486. No `systemd-nspawn` container
is used. No 9p/virtfs/smb/`fat:` host drive, no `-netdev user` hostfwd, no
guest-reachable QMP/monitor, no virtio-serial host channel. Launcher:
`streamhost/stations/os213/qemu-streamhost.sh`.

## Traps

1. **The Microsoft 1.30.1 Server preinstalled image was the wrong image, not
   a device-set problem.** It boots to the genuine
   `Microsoft (R) Operating System/2 Version 1.3` banner, then clears the
   screen, prints a truncated `TRA` — almost certainly the head of an OS/2
   `TRAP xxxx` panic — and wedges for good (no framebuffer change across
   45 s). Four device-set theories were raced against it (explicit CHS
   geometry, a `pc-i440fx` machine, a RAM/CPU sweep, and an `-icount`
   CPU-speed-bug probe) and every one either regressed or reproduced the
   identical wedge — including the `-icount` theory, which ruled out the
   well-known OS/2 1.x "CPU too fast" timing bug (the wedge persisted
   unchanged through ~120 s of throttled wall clock). The image itself is
   unbootable for this fleet and is abandoned; the station installs fresh
   from the IBM 1.30.2 SE floppy set instead, which boots straight to the
   `IBM Operating System/2 Installation Version 1.30` welcome screen with
   the framebuffer settled 5.2 s after launch.
2. **Never pin disk CHS geometry on the `-drive` line.**
   `-drive file=...,format=qcow2,cyls=310,heads=16,secs=63` is rejected
   outright by QEMU 11 — `Block format 'qcow2' does not support the option
   'cyls'`. Geometry only goes on `-device ide-hd`, and even there, pinning
   the source VMDK descriptor's 310/16/63 made the boot worse than letting
   QEMU auto-detect.
3. **`-machine pc-i440fx-11.0` and low RAM both freeze at SeaBIOS**, not at
   an OS/2-specific fault — both stall at "Booting from Hard Disk..." before
   any OS/2 code runs, which is a useful tell that the failure is in the
   PCI/BIOS path, not the guest.
4. **`isa-vga` stripes every PM fill under KVM.** Each 8-pixel VGA byte gets
   only its high nibble written: a white window interior over the grey
   desktop reads 4 px white / 4 px grey across every row, title bars become
   green hatching, the menu bars never appear. It is the card, not the
   machine — raced 2026-09-24 on `-display none` clones of the golden disk:
   `isa-vga` striped on `isapc` and on `pc`; `isa-cirrus-vga` on `isapc`,
   and `-vga std`/`-vga cirrus` on `pc`, all drew cleanly. QEMU's own
   `screendump` shows the stripes, so it is not the stream. The first golden
   and the poster were baked striped; both were redone on `isa-cirrus-vga`.
