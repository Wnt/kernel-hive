# os213 — Microsoft OS/2 1.30.1, Presentation Manager

IBM OS/2 1.3 (1990; Presentation Manager itself debuted in OS/2 1.1, 1988) —
the last operating system IBM and Microsoft shipped together, six months
before Windows 3.0 ended the partnership. This station runs the Desktop
Manager shell of OS/2 1.x, the predecessor to the Workplace Shell that
arrived with OS/2 2.x/Warp. It sits beside `nt351` and `os2warp` as a third
point in the museum's IBM/Microsoft desktop lineage, at the 16-bit
protected-mode end of it.

## Install recipe

The station installs from the 10-floppy IBM Standard Edition set (`Install`,
`Disk01`-`Disk05`, `Driver1`-`Driver4`) onto a FAT hard disk, under 16 MB RAM
on an ISA machine with no PCI bus. Media is swapped over QMP
`blockdev-change-medium` on the `fd0` backend during install; the daemon
waits on framebuffer proof (`fb-wait.py --change`/`--settle`), never a
relaunch per disk or a guessed sleep.

## Device set

```text
qemu-system-i386 -name streamhost-os213 \
  -accel tcg -m 16 -smp 1 \
  -machine isapc -cpu 486 \
  -rtc base=localtime \
  -boot c \
  -device isa-vga \
  -display dbus,p2p=on,audiodev=snd0 \
  -audiodev dbus,id=snd0,out.frequency=48000,out.channels=2,out.format=s16 \
  -device sb16,audiodev=snd0 \
  -drive file=os213-golden.qcow2,format=qcow2,if=none,id=hd0 \
  -device ide-hd,drive=hd0,bus=ide.0,unit=0 \
  -qmp unix:qmp.sock,server=on,wait=off
```

- `-machine isapc -cpu 486`: OS/2 1.x predates PCI entirely. A
  `pc-i440fx-11.0` machine freezes this guest at SeaBIOS's "Booting from Hard
  Disk...", well before the OS/2 banner. `isapc` has no KVM path, so the
  station runs under TCG — acceptable, since OS/2 1.3 is a tiny, low-clock
  workload for a modern host.
- `-m 16`: 16 MB is the working point; `-m 8` also froze at the same SeaBIOS
  stage in the race.
- Disk geometry is left to QEMU's auto-detection on `-device ide-hd`. No
  `cyls=`/`heads=`/`secs=` anywhere — see Traps.
- `-device isa-vga`: Presentation Manager runs plain VGA at 640x480x16.
- Pointer: `qemu-ps2-relative` — see below.
- No `-net`/`-netdev` line at all: OS/2 1.3 ships no TCP/IP stack.

## Pointer

PS/2 relative only: `-machine isapc` has no USB bus, so `usb-tablet` — and
with it every USB absolute route the fleet otherwise uses — is unavailable
here. This is the machine's only transport, not a shortcut.

**The guest's mouse stack is present and complete.** Read out of the disk
image (`CONFIG.SYS`, verbatim):

```text
DEVICE=C:\OS2\POINTDD.SYS
DEVICE=C:\OS2\MSPS201.SYS
DEVICE=C:\OS2\MOUSE.SYS TYPE=MSPS2$
DEVICE=C:\OS2\PMDD.SYS
```

`MSPS201.SYS` is the Microsoft PS/2 mouse device driver and `MOUSE.SYS
TYPE=MSPS2$` binds to it; `POINTDD.SYS` + `PMDD.SYS` are the pointer-draw
pair Presentation Manager draws the sprite with. The earlier "maybe this
pre-installed image has no mouse driver" lead is **disproven** — do not
re-run it.

**Clicks work.** The 2026-09-13 `changed=0` click result was an aiming
failure in the test harness, not a guest fault. Measured on a rig clone
(`fb-react`-style masked pixel diff of QMP `screendump` frames):

| Step | Result |
|---|---|
| single left click on a Group-Main item (QMP `input-send-event` `btn`) | changed=**3631**, bbox 256,171-479,332 — the selection moved |
| double click on the same item | changed=**94050**, bbox 56,56-559,375 — **OS/2 System Editor opened** |

Both `input-send-event` `btn` and HMP `mouse_button 1` / `0` deliver the
button; nothing about the button path was ever broken.

### The 2:1 mickey ratio — why aiming failed, and why one scale cannot fix it

OS/2 1.3's mouse driver uses the classic **2:1 horizontal:vertical mickey
ratio**. Measured from a homed pointer with single-unit `rel` events,
0.004 s apart, on the station's own device set:

| Sweep | Units sent | Pixels moved | Gain |
|---|---|---|---|
| 50 x `rel x=+1` | 50 | 51 | **1.02 px/unit** |
| 50 x `rel y=+1` | 50 | 25 | **0.50 px/unit** |
| 20 x `rel x=+10` | 200 | 177 | 0.885 px/unit (the driver's acceleration curve bends above ~1 unit/event) |
| 20 x `rel y=+10` | 200 | 100 | 0.50 px/unit |

So a commanded position derived from relative deltas lands at roughly
**twice** the intended vertical distance from where the harness thought the
pointer was — far enough that every click in the first bake fell on empty
desktop. Aim with single-unit events and halve the y count and the clicks
land.

This is also why `SH_CURSOR_SCALE` cannot linearise this station: the daemon
exposes **one** scalar (`streamhost/src/config/mod.rs`), and this guest needs
x=1.0 with y=0.5. Setting either value breaks the other axis. The station is
therefore left at `SH_CURSOR_SCALE=1.0` (the default) and the route to a real
1:1 pointer is absolute, not a rescaled relative one.

### Absolute via `kh-ramabs` — derived, NOT yet verified (OPEN)

The route is `docs/lab/BEOS-ABSOLUTE-POINTER.md`: write the guest's own
pointer coordinate into guest RAM and nudge PS/2 by one unit so the guest
republishes it. `-device kh-ramabs` lives only in the forked build at
`/opt/qemu-beos/bin/qemu-system-x86_64` (11.0.2, same version as pve-qemu),
which accepts `-enable-kvm -machine isapc -cpu 486` unchanged and cold-boots
this disk to the PM Desktop Manager.

A bias search over the full 16 MB of guest RAM (`scripts/dev/os213-ramabs-derive.py`,
five located pointer positions, `pmemsave` after each) found the pointer
coordinate stored as an **`int16` x,y pair at bias (0,0)** — i.e. the guest
holds the exact screen pixel, and the PM arrow's hotspot is its top-left tip,
so the sprite origin IS the pointer. Candidates from a cold boot:

| Address | Note |
|---|---|
| `0x0019514` | low memory — most likely `POINTDD.SYS`'s own copy |
| `0x010fe20` | part of an x,y,x,y quad (`0x10fe20`/`0x10fe24`) |
| `0x010fe24` | the second half of that quad |
| `0x0024ea0`, `0x0024eb0`, `0x00253b0`, `0x00253ca` | y-then-x order; `layout=point16le` cannot address these as-is |
| `0x010c624` | x with **inverted** y (`bias=(0,479)`) — PM's bottom-left origin space |

`0x0019514` and `0x010fe20` were tested with the device's own connect-time
write probe and **both report `verified=no probefail=1`** — the guest
overwrites the location faster than the probe reads it back, or the address
moved between boots. The remaining candidates are untested.

**Two traps for whoever finishes this:**

1. **The PM pointer leaves XOR trails.** Rapid relative motion (1-unit events
   a few ms apart) leaves dashed diagonal residue across the desktop that a
   naive "largest changed blob" locator latches onto instead of the sprite —
   the second derive run reported the pointer frozen at one position for five
   moves because of it. Settle after each move and re-shoot the reference, or
   locate with `scripts/dev/cursor-locate-cv.py` (this is an XOR cursor, so
   `cursor-locate.py` reports AMBIGUOUS everywhere — measured).
2. **Addresses are bound to one boot.** Derive against the same boot the
   golden is captured from, exactly as `pcgeos-ramabs-derive.py` warns.

Next command, verbatim:

```sh
ssh lab 'python3 /tmp/ramtest.py 0x10fe24'   # then 0x10c624 with an inverted-y layout
```

with the rig at `/data/vms/sandbox/os213-ptr/ramabs/` (its `launch.sh` takes
`$EXTRA` and `COLD=1`, and already runs `/opt/qemu-beos`).

## Network

None, deliberately. OS/2 1.3 ships no bundled TCP/IP stack (IBM TCP/IP for
OS/2 1.3 was a separate product IBM sold on its own), so os213 is off the
retronet: it has no `rn-tapnet.sh`, and per AGENTS.md rule 15 none is
committed until a station is proven — this one has no path to be proven, so
retronet stays an open, deliberately-unfilled item rather than a pending
task.

## Sandbox verdict

os213 is an emulated machine under the fleet QEMU, not a host application —
the visitor's reach ends at the emulated i486. No `systemd-nspawn` container
is used. No 9p/virtfs/smb/`fat:` host drive, no `-netdev user` hostfwd, no
guest-reachable QMP/monitor, no virtio-serial host channel. Launcher:
`streamhost/stations/os213/qemu-streamhost.sh`.

## Traps

1. **The Microsoft 1.30.1 Server preinstalled image was the wrong image, not
   a device-set problem.** It boots to the genuine
   `Microsoft (R) Operating System/2 Version 1.3` banner, then clears the
   screen, prints a truncated `TRA` — almost certainly the head of an OS/2
   `TRAP xxxx` panic — and wedges for good (no framebuffer change across
   45 s). Four device-set theories were raced against it (explicit CHS
   geometry, a `pc-i440fx` machine, a RAM/CPU sweep, and an `-icount`
   CPU-speed-bug probe) and every one either regressed or reproduced the
   identical wedge — including the `-icount` theory, which ruled out the
   well-known OS/2 1.x "CPU too fast" timing bug (the wedge persisted
   unchanged through ~120 s of throttled wall clock). The image itself is
   unbootable for this fleet and is abandoned; the station installs fresh
   from the IBM 1.30.2 SE floppy set instead, which boots straight to the
   `IBM Operating System/2 Installation Version 1.30` welcome screen with
   the framebuffer settled 5.2 s after launch.
2. **Never pin disk CHS geometry on the `-drive` line.**
   `-drive file=...,format=qcow2,cyls=310,heads=16,secs=63` is rejected
   outright by QEMU 11 — `Block format 'qcow2' does not support the option
   'cyls'`. Geometry only goes on `-device ide-hd`, and even there, pinning
   the source VMDK descriptor's 310/16/63 made the boot worse than letting
   QEMU auto-detect.
3. **`-machine pc-i440fx-11.0` and low RAM both freeze at SeaBIOS**, not at
   an OS/2-specific fault — both stall at "Booting from Hard Disk..." before
   any OS/2 code runs, which is a useful tell that the failure is in the
   PCI/BIOS path, not the guest.
