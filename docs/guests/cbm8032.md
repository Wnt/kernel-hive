# Commodore CBM 8032 (1980) — gallery tile notes (udp/54109)

**Guest:** a captured **Debian 13 (trixie) x86_64 kiosk** running **VICE `xpet -model
8032`**, emulating the **80-column business PET** at its power-on BASIC 4.0
prompt. An **"emulator bridge"** tile — streamhost captures the Linux
framebuffer + AC97 audio exactly like every other tile. See
**`streamhost/docs/BRIDGE.md`**.

**Shared base:** `/data/vms/bridge/bridge-base-trixie.qcow2` — already contains the
whole VICE family.
**Build script (tile):** `scripts/build-guests/tiles/cbm8032.sh` — thin overlay +
kiosk `launch.sh` + ROM repair + quiet console + golden bake + a two-step
framebuffer proof of the demo listing, fully automated, ~2 minutes.
**Tile dir (host):** `/data/vms/streamhost/tiles/cbm8032/`.
**Registry entry:** `registry/tiles/cbm8032.json` (slot 109, udp 54109, VMID
225, ssh hostfwd 127.0.0.1:5825).

## Media and license — there is none to stage

Like `vic20` and `plus4`, and for the same reason: VICE bundles the Commodore
ROMs, and a CBM 8032 needs nothing else at all to reach BASIC — no disk, no
cartridge, no tape. No external media, no licensed image, no `check-assets.sh`
row.

- **VICE 3.9** — GPLv2; bundles the PET BASIC 4.0 / KERNAL 4 / editor /
  character ROMs for emulation use.

`-model 8032` resolves to four ROM files, via `src/pet/petmodel.c` (`RAM_32K`,
`COLS_80`, `KBD_TYPE_BUSINESS_UK`) and `src/pet/petrom.h`:

| ROM | File |
|---|---|
| BASIC 4.0 | `basic-4.901465-23-20-21.bin` |
| KERNAL 4 | `kernal-4.901465-22.bin` |
| 80-column business editor, 50 Hz | `edit-4-80-b-50Hz.901474-04_.bin` |
| character generator | `characters-2.901447-10.bin` |

`cbm8032.sh` copies `/usr/local/src/vice-3.9/data/PET/` into
`/usr/local/share/vice/PET/` and **asserts those four basenames** — the same
`make install` gap that bit the C64 and the VIC-20, where a missing ROM makes
VICE segfault at startup with no output whatsoever.

## The fixture, and how a visitor drives it

The golden is **the machine's own untouched power-on screen**:

```
*** commodore basic 4.0 ***

 31743 bytes free

ready.
```

green on black, 80 columns wide, block cursor under `ready.`. Nothing is
curated and nothing is typed into it — the lesson from the Plus/4 add, whose
first golden rested inside an application and dropped visitors into the middle
of a program with no way to tell what it was or how to leave.

That leaves a starker exhibit than any of its siblings, which is the honest
thing: on this machine the BASIC prompt genuinely **is** the user interface.
The affordance therefore lives in the SPA, as the registry `demoProgram`:

| Step | What happens |
|---|---|
| **Type in a demo program** | the SPA types the five-line listing below, one line at a time, at 170 ms per character |
| the visitor presses `RETURN` | `run` is typed WITHOUT its newline — starting the program is the visitor's act, not the gallery's |
| result | a 12x8 times table printed with `tab()` across all 80 columns |

```basic
10 print chr$(147)
20 for r=1 to 12
30 for c=1 to 8
40 print tab((c-1)*10);r*c;
50 next c:print:next r
```

### No `keyboard` block, and why

The 8032 has the **business** keyboard (`KBD_TYPE_BUSINESS_UK`), and VICE's
matching symbolic keymap `sdl_buuk_sym.vkm` maps host ASCII straight onto that
matrix. Every character the listing needs — `$ ( ) * ; : -` included — was
verified by framebuffer to arrive as itself, so there is no `charMap`.

Nor is there a `letterCase: upper-only` flag, unlike `vic20` and `mpf2`. The
business editor ROM comes up in **text mode**, where an unshifted letter
displays as lower case and BASIC accepts it — which is why the machine's own
banner reads `*** commodore basic 4.0 ***` in lower case, and why the listing
above is written that way.

Useful host keys under that keymap, for anyone driving the tile by hand:

| Host key | 8032 key |
|---|---|
| `Esc` | RUN/STOP |
| `F1` | the business keyboard's own ESC |
| `Home` | CLR/HOME |
| `PageUp` | RVS OFF |
| `PageDown` | RPT |
| `End` | the `←` PETSCII key |

There is **no Commodore key and no RESTORE key** on this machine — both are
C64-era additions — so the `c64` on-screen-keyboard profile is the wrong one
here.

## Device set and launcher

Identical in shape to its bridge siblings (`c64`, `vic20`, `plus4`, `apple2`,
`atarist`, `amiga`, `mpf2`) except for its memory — see
`streamhost/tiles/cbm8032/qemu-streamhost.sh`. The kiosk launcher is:

```
xpet -model 8032 -sounddev alsa -CRTCdsize
```

on a **1600x1200** X root. As for every VICE tile, **the kiosk profile must not
redirect `startx`'s output to a file**: VICE 3.9 segfaults in `vice_banner()`
whenever stdout is not a terminal and prints nothing at all — backtrace and
symptom in [`vic20.md`](vic20.md).

### Why 1600x1200, measured

There is no window manager, so an SDL window larger than the X root is silently
clipped and mispositioned — recon's first attempt at this machine left only the
tail of `ytes free` visible on 1024x768. Measured on a soltest clone by painting
the X root navy and taking the bounding box of everything that was not navy:

| Flags | SDL window | 1024x768 | 1600x1200 | 1920x1080 |
|---|---|---|---|---|
| (none) | 704 x 532 | fits | fits | fits |
| `-CRTCdsize` | **1408 x 1064** | **clipped** (1064 > 768) | fits, 96/68 slack | fits, 256/8 slack |

1600x1200 ships: it is the tightest advertised mode that contains the doubled
window (78% of the captured frame is the emulated screen, against 72% at
1920x1080), it costs fewer scanout pixels, and its 4:3 shape is the shape of the
machine's own 12-inch monitor. Undoubled would fit 1024x768 but throws away half
the resolution of an 80-column screen, which is the whole subject of the exhibit.

Note there is **no `-CRTCborders`**. Unlike VIC-II/TED/VIC, VICE's CRTC video
chip has no border resource, so the sibling tiles' `-XXXborders 0` has no
counterpart and the border (64 px each side horizontally, 82 vertically at
`-CRTCdsize`, around a 1280x900 text area) stays. Passing it is not ignored:
`Unknown option '-CRTCborders'. Error parsing command-line options, bailing
out.` — xpet exits and takes X with it.

### Memory: 768 MB, not 1536

Half what the other bridge tiles carry. With `xpet` up at 1600x1200 the guest
reports **MemAvailable ~390 MB** (399292 kB on the build that shipped), so the
headroom is real; `assert_memory()` re-checks a 200 MB floor on every build and
fails the build rather than quietly shipping a swapping guest. Host-side the
tile's QEMU sits at **~715 MB RSS**.

## Keyboard pacing

`SH_KEY_MIN_HOLD_MS=80`, `SH_KEY_MIN_GAP_MS=80` — four frames each way. The
8032's editor ROM is the 50 Hz (European) one that `-model 8032` selects, so a
frame is 20 ms and the playbook's two frames would be 40/40.

**Carried over from the VIC-20's bisect rather than re-measured**: same
emulator, same 50 Hz frame, same host, and the failure those numbers guard
against is a host scheduling stall on a box running 30+ emulators rather than a
property of the emulated machine (`scripts/dev/emu-key-pacing-bisect.py`:
40/40 corrupted 1 line in 22, 80/80 none in 22 — see [`vic20.md`](vic20.md)).
Re-bisect if this tile ever drops characters.

`demoProgram.perCharMs` is **170**, above the 160 ms drain rate those two knobs
impose; `scripts/tiles-registry.py validate_demo_pacing` enforces the relation.

The shared fleet streamhost binary does **not** implement `SH_KEY_MIN_HOLD_MS`.
Like `vic20` and `plus4`, this tile is pinned to the canary build
(`/usr/local/lib/streamhost/tiles/cbm8032/{current,previous}` →
`streamhost-bca88a2bed22e1ea616993995faf4379b954bb11`) that does.

## Verification (2026-08-09)

Evidence in `/data/vms/streamhost/tiles/cbm8032/evidence/`:

| Artifact | Shows |
|---|---|
| `cold-boot-basic.png` | the first cold boot after ROM repair reaching BASIC 4.0 |
| `ready-before-golden.png` | the untouched power-on screen — **the frame that was baked** |
| `golden-restored.png` | `loadvm golden` immediately after the bake |
| `keyboard-1-listing.png` | the registry listing typed after the bake, at the tile's own 80/80 pacing |
| `keyboard-2-run.png` | `run` — the 12x8 times table across all 80 columns |
| `golden-restored-after-keyboard.png` | `loadvm golden` returning to the exact baked screen |
| `live-tile-serving.png` | the same fixture captured from the RUNNING `streamhost@cbm8032`, 1600x1200 |

Each step asserts what is on the screen, in green-pixel counts: idle banner
**1985**, listing typed **3861**, RUN **7342**.

**The readiness predicate is a band, not a floor, and that is load-bearing.**
The PET's screen RAM is uninitialised at power-on, so for the first moments
after `xpet` starts the CRTC paints all 2000 cells of random bytes as random
glyphs — a solid green block. The first version of this builder's predicate
accepted that frame at **375726** green pixels and logged "BASIC 4.0 screen
present"; it would have baked it. Real PET text is sparse, so `wait_for_basic()`
now requires `1200 < green < 20000` and `assert_root_size()` additionally reads
the capture's own PPM header to prove the 1600x1200 xrandr mode took.

**One honest caveat.** During development, one RETURN out of roughly thirty sent
over QMP at 80/80 did not commit its line — the letters `run` were on screen and
the program had not started. A deliberate four-trial retest of the same sequence
was 4/4 clean, and all five listing lines commit reliably on every build, so it
looks like a one-off host scheduling stall rather than a pacing error. It cannot
affect the exhibit as configured: the SPA types `run` **without** its newline and
the visitor supplies the RETURN.

## Cold boot and rollback

Zero input is genuine, and because the golden is the power-on screen itself, a
cold boot and a restore reach the same place. See
`scripts/coldboot/cbm8032-zero-input-prep.md`.

To withdraw the tile: `systemctl stop streamhost@cbm8032`, set
`enabled: false`, regenerate, republish the three runtime documents (tiles.json, gallery-manifest.json AND golden-manifest.json — the third is the reset allow-list). To rebuild:
`scripts/build-guests/tiles/cbm8032.sh --force`, which replaces `overlay.qcow2` and so
**destroys the golden inside it**, then bakes and re-proves a new one.
