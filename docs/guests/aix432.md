# aix432 guest — IBM AIX 4.3.3 with CDE (RS/6000 7020 "40p", PowerPC/PReP)

Status: **CANDIDATE — not on the floor, not in any lineup.** The registry entry
is `enabled: false` / `lifecycle: candidate`; slot **201** / UDP **54201** and
retronet **10.99.0.28** are claimed, nothing is deployed. The desktop, the
browser and the game all render on the emulated card; what is missing is a
tracked launcher, a restore-proven golden, and a relay-reachable port (see
[Promotion](#what-still-gates-promotion)).

Research note — **read it before touching anything here**:
[`docs/lab/research/candidate-aix.md`](../lab/research/candidate-aix.md). It is
the source of truth for what this machine is and what is honest to claim about
it. This page is the operator's summary of it.

## Identity and source

- Public ID / station directory: `aix432`
- Archetype: `beige-tower-crt`
- Target: **AIX 4.3.3 with X11R6 / Motif 2.1 / CDE**, on `qemu-system-ppc -M 40p`
  (IBM RS/6000 7020 model 40P), rendering **natively into an emulated
  framebuffer** — no remote X, no XDMCP. That constraint is the whole exhibit:
  the Virtual OS Museum's "graphical AIX" is an Xephyr XDMCP session with
  host-supplied fonts, which this lab has ruled out.
- **It is 4.3.3, not the originally scoped 4.3.2, and that is deliberate.**
  AIX 4.3.2's installer kernel stops driving the emulated LSI 53c810 after one
  retry cycle and hangs at 100 % CPU forever; 4.3.3 streams ~1100 reads and
  installs fine. Same firmware, same media layout, same patches — measured, not
  assumed (research §1). The **4.3.2 Bonus Pack** is installed on top, which is
  where Ultimedia Services and Netscape come from.
- Media: see [`ASSETS-MANIFEST.md`](../lab/ASSETS-MANIFEST.md) — AIX 4.3.3
  Volumes 1-4 (volume 1 is the only bootable one; it carries the type-0x41 PReP
  boot partition), the 4.3.2 install set and Bonus Pack CD1+CD2, the GXT130P
  support software, CorelDRAW 3.5 for UNIX, IBM's own AIX game binaries, and the
  firmware ROMs. **Preservation class throughout**: IBM commercial software with
  no redistribution grant. Private exhibit only — never committed, never served.

Three things live only on the `aix432-s3` branch, and the station does not work
without any of them:

1. **Hervé Poussineau's S3 Trio card** (2017, never merged upstream), forward-
   ported to 11.0.2. It gives *Open Firmware* a framebuffer instead of the
   serial console every published AIX-on-QEMU recipe uses. **AIX itself can
   never bind to it** — AIX 4.3 has no S3 driver of any kind (research §4).
2. **`hw/display/mga.c`**, new — the Matrox behind the GXT130P, which is what
   AIX *can* bind to, including the 2D engine the DDX actually uses (ILOAD
   colour-expansion, BITBLT, LINE/AUTOLINE, TRAP, per-op clipping).
3. **Artyom Tarasenko's AIX fixes** (53c810 register hiding, raven PCI I/O
   decoding, lsi reentrancy) plus **a PS/2 fix**: AIX's `kbddd` programs scancode
   set 3 per-key make/break with `0xFC` followed by a *list* of key numbers, and
   QEMU ACKed only the first and RESENT the rest — which failed the keyboard
   watchdog, failed `lftKiInit`, and made **every `/dev/lft0` open fail**.

## The firmware is the exhibit

The single most surprising fact about this station: **the graphics stack comes
up because of the boot ROM, not because of the display model.**

AIX drives graphics through `gxme0` (Graphics Data Transfer Assist) → `rcm0` →
the `aixgsc` syscall gateway → the adapter DDX. `cfggxme_rspc` configures
`gxme0` by enumerating **PReP residual-data device packets**, and Open Firmware
builds that structure itself. Under Tarasenko's OF, `gxme0` and `rcm0` stay
`Defined`, `aixgsc` never registers, the DDX dies, and X does not start — with
the display model completely innocent (zero MGA registers touched).

Under the **genuine IBM ROM**, the authentic residual data brings up `gxme0`,
`rcm0`, `mg21`, `lft0` **and `paud0`** with **no guest patching at all** —
`rcm_load` `cmp`-verifies pristine — and CDE renders. Two changes make that ROM
boot:

- **`PREP_TB_FREQ=15000000`** — a new environment override on the fork. The
  firmware assumes a 15 MHz timebase (66.67 ns/tick constants); QEMU offers
  100 MHz.
- **skip the single POST `settimeofday` call** (the `bl` at `0x74da8`). The real
  7020-40P shipped a **PowerPC 601**, whose RTCU/RTCL count {sec,nsec} natively;
  QEMU has no 601 model, so the firmware takes its **604 fallback path**, stores
  the clock offset as negated packed {sec,nsec} and adds it back **as ticks** —
  then asserts *"time went negative"* and spins in an LED-flash loop at
  `0x358c0` displaying crash code **888-102-700-0A5** on an operator panel QEMU
  does not have. That is what a "frozen splash at 50 % CPU and no serial output"
  actually was.

**The skip is currently a GDB-RSP helper, and that is debt**: it should become a
QEMU-side option rather than a gdbstub babysitter. Seeding NVRAM with a valid
date/config is an untested alternative. A station that needs a debugger attached
to boot is not a station that can be brought up by `systemctl`.

## Traps, in the order they bite

1. **`-M 40p` has no IDE.** `block_default_type` is `IF_SCSI`, so `-hda` and
   `-cdrom` both land on the LSI. The ROM's `/pci/ide/...` devaliases are stale
   and `dev /pci ls` shows no IDE node at all.
2. **Autoboot never works.** OF tries `/pci/ethernet` and gives up. Interrupt it
   with a few CRs and boot explicitly: `boot cdrom:2` to install, `boot disk`
   afterwards.
3. **RAM is capped.** `-m 512` is refused outright ("try 192 MB"); OF reports
   128 MiB whatever you pass, matching `default_ram_size`.
4. **Do not move the SCSI controller.** AIX's bootstrap has `pci1000,1@c,0`
   baked into its strings, which makes slot 12 look right. It is not: OF
   enumerates a fixed set of slots and moving the LSI to 12 makes it vanish from
   the device tree entirely. 4.3.3 boots fine from slot 1.
5. **Audio needs `-global cs4231a.dma=6`.** AIX's CS4231 driver fixes play DMA
   at 6; QEMU defaults to 3. iobase and IRQ already match.
6. **Two red herrings, both already chased.** `invalid/unsupported opcode:
   00 00 00 00 @ 07ea6390` in the QEMU log appears on the *successful* 4.3.3
   boot too. And the SCSI BARs reading back unmapped at the `ok` prompt is
   normal — OF clears them during its own PCI probe, and pre-assigning them from
   `ibm_40p_init` does not help. Both patches were tried and reverted; **do not
   re-derive them.**

## The pointer is a closed loop

The 40p has a PS/2 mouse and no absolute device of any kind, so this station
began where every other relative-pointer station in the fleet still is: the
daemon **dead-reckoned** absolute coordinates, pinning the guest cursor into a
corner once and then pushing deltas from a belief (`SH_INPUT_BACKEND=dbus-rel`,
`streamhost/src/rel_bridge.rs`). Guest acceleration, an edge clamp or an X warp
invalidates that belief silently, and only the visitor shoving the cursor into a
corner ever re-syncs it.

It never had to. AIX's GXT130P DDX drives the **hardware cursor**, so the guest
writes its own pointer position into the DAC's CURPOSX/CURPOSY registers on
every move, and `hw/display/mga.c` can read them. The loop therefore closes
**inside QEMU**, at the emulator's own rate and with direct register access —
exactly as `irix` runs its MOVEA engine inside MAME over the Newport VC2's
cursor registers ([`IO-PATHS.md`](../IO-PATHS.md), the closed-loop rows).

    err = target - reading - hotspot - in-flight
    counts = trunc(err / (gain x margin)), capped, ONE step per window

The control law and its three binding rules — the in-flight balance, never a
step opposing the measured error, and the oscillation latch — are ported from
the landed irix engine, whose dead ends are recorded in
[`irix.md`](irix.md#movea-engine--closed-loop-over-the-reading-2026-08-04).
Gain is a **step sizer only**: it decides how far one window may reach, never
where the pointer ends up, so a wrong gain costs convergence speed and never
accuracy. Measured on the desktop below: every target converges to ±1 px with
zero give-ups, and a click on Netscape's Back button repaints the page.

Two things this guest does that the irix rules do not cover, both found on the
framebuffer and both load-bearing:

- **Never issue while the last step is still on the wire.** The in-flight
  balance decays on a schedule while a TCG guest absorbs a PS/2 packet on its
  own, so the estimate is long gone before the motion arrives and the loop
  re-issues counts already in flight. Measured before the gate existed: two
  windows of −48 counts against an unchanged reading, a 288 px overshoot, and
  an oscillation that accepted 30 px off target. The registers moving is the
  only evidence a step landed. The gate is **bounded at 6 windows**, because
  against the guest's screen clamp they never move again and an unbounded gate
  wedges the pointer for the rest of the session — which is exactly how it
  first failed.
- **The hotspot is read at the write, never guessed.** The registers hold the
  cursor SPRITE's origin, so the reading is `pointer − hotspot`, and every glyph
  has a different one: the CDE root window's X_cursor is a saltire whose hotspot
  is its CENTRE (7,7), the desktop arrow's is (1,1), the window resize bar's is
  (14,7). Drive the READING onto the target with the wrong hotspot and both the
  drawn cursor and the click land that far from the visitor's mouse.

  Two facts name it, and between them they cover the session:

  1. **A screen clamp**, which pins the pointer at 0 (or W−1) by construction,
     so whatever the registers then read is the negation of the hotspot on that
     axis. `mga_ptr_home` forces one at connect and `mga_ptr_step` takes one
     whenever a visitor's target sits on an edge — which is what the deliberate
     over-clamp in there is for.
  2. **The compensating write a glyph swap forces**, which is the hotspot delta
     exactly, because a swap does not move the pointer.

  Fact 2 is only usable if the compensation can be told apart from motion, and
  that is a question about *where you look*, not about statistics. Sampling the
  registers once per engine window cannot do it — the baseline is a window old
  and a TCG guest's lagging motion is mixed into it, which is how an early
  attempt walked the hotspot to −67 px in one sweep. The DDX states the position
  as a fixed group of four bytes — **XH, XL, YL, YH** — and a swap's
  compensation is **always a group of its own**. Measured over a captured
  magnet: 307 swap groups, every one a pure compensation and perfectly
  antisymmetric (`b458→6f76` is −7,0 and `6f76→b458` is +7,0, 150 times each),
  while ordinary motion groups in the same capture carried deltas of 48, 144 and
  244 px and never a signature change. So the group boundary **is** the
  isolation, and the delta is recorded there — the same place irix records its
  VC2 swap accumulator, and for the same reason.

  The rule the engine then applies is **continuity**: the hotspot absorbs the
  compensation exactly and the believed pointer comes out unchanged. That is not
  an estimate of the new hotspot; it is the fact that nothing moved. A
  derivation is only as good as the hotspot it starts from, so it inherits
  `hot_exact` rather than claiming it — and once a chain starts from a clamp,
  every glyph it reaches is exact and is remembered under a **signature over the
  sprite bytes**, so a glyph is measured once, ever.

### The magnet, and why a guessed hotspot is not a small error

Reported from the floor: over a window's resize bar the cursor twitches back and
forth, "magnetic". It is the same shape as the irix "repelling magnet" and it is
worth keeping, because the failure looks like a control-loop problem and is not.

Before the write-time derivation, a glyph no clamp had named fell back to (0,0).
No clamp reaches a window frame, and the resize glyph's hotspot is really
(14,7) — so crossing onto the bar moved the believed pointer 14 px, the loop
corrected, the correction re-crossed the border, and the glyph swapped back.
Reproduced programmatically with a target that never moves:

| | steps issued | glyph flips | re-aims |
|---|---|---|---|
| before, 8 s at 917,557 | 386 | 660 | 110 |
| after, 8 s at 917,557 | **0** | **0** | **0** |

Two things had to change. The hotspot had to become a measurement (above), and
**a re-aim now requires `hot_exact`** — the at-rest pass moves the guest's
pointer on the loop's own authority, and if the number behind it is a guess that
authority is not there. Either alone leaves the cycle turning.

The engine now derives the resize glyph at (14,7) and the desktop arrow at
(1,1), which is independently what the antisymmetric swap deltas say they must
be — three separate paths through the capture agree.

### Two bugs this work exposed### Two bugs this work exposed

- **The sprite's plane rows are byte-reversed in VRAM.** AIX's DDX uploads the
  64x64x2bpp shape with 64-bit stores — what a PowerPC graphics driver
  naturally uses for a bulk copy — and they land byte-swapped in the model's
  little-endian aperture. Read the wrong way round the cursor still renders and
  still tracks the mouse, which is why bring-up accepted it; it just draws
  **~48 px to the right of the actual pointer**. No open-loop pointer test can
  see that, and a 1:1 cursor cannot live with it. Dumped from
  `0xC3000000 + XCURADD<<10` with a cursor on screen: only the reversed reading
  produces a cursor at all.
- **The DAC position bias is 64, and the measurement says 57.** At the top-left
  clamp the registers read 57, on both axes, at both corners — which looks
  exactly like a bias off by 7 and is not: the glyph there is the X_cursor,
  whose hotspot is its centre, so the sprite origin is *supposed* to sit 7 px up
  and left of the pointer. Subtracting 57 draws the X 7 px down and right of
  where a click lands. The 7 is a hotspot, and hotspots belong to the pointer
  engine, not to the DAC.

### Operating it

- `-global mga.ptrctl=<chardev>` arms the engine; without it the device behaves
  exactly as before — no timer, no handlers, no injection — and that is also
  the **rollback**, paired with `SH_INPUT_BACKEND=dbus-rel` in the env fixture.
- **Single injector (binding).** While the socket is connected the engine owns
  the guest's pointer completely. Nothing else may push motion or button edges
  at that mouse — not the dbus-rel bridge, not `input-send-event` over QMP, not
  a `labctl` pointer helper — or the two fight over the guest's PS/2
  accumulator and neither knows where the cursor is. Keys are unaffected: they
  still ride the ordinary QEMU/dbus keyboard path.
- Tunables are device properties, all with working defaults:
  `ptr-window-ms` (16), `ptr-deadband` (1), `ptr-move-step` (48), `ptr-tries`
  (40), `ptr-btn-gap-ms` (24), `ptr-gain-x100` (300 — the measured px/count on
  this guest; too HIGH only costs windows, too LOW overshoots),
  `ptr-hotspot` (on), `ptr-trace`, `ptr-trace-pos`.
- `STAT` over the socket reports the reading, the hotspot and whether it was
  measured, the learned gain, the queue, the residual and the counters. It is
  the first thing to look at for any pointer complaint here.
- **No migration state is added.** Every engine field is derived from the
  registers or the live connection and re-bases itself after a `loadvm`, so the
  vmstate signature is unchanged and the golden is untouched — proven by
  restoring it under the new binary. **Install order matters**: the binary must
  be in place before the launcher, because `-global mga.ptrctl=` on the previous
  binary is an unknown property and QEMU refuses to start.

## The exec channel

`labctl exec aix432 "<cmd>"` — real captured stdout+stderr and the guest's own
exit code, over **AIX's own telnetd at `10.99.0.28:23`**, dialled from labhost
across the retronet tap. `exec_kind: telnet_unix_e`, the kind `sunos414` and
`beos` already share, so there is no new client and no agent in the guest.

**This page used to say there would never be a network exec channel, "because
the guest has no route off the bridge". That was the wrong direction.** The
guest still has no route off the bridge and never gets one — `AIXRN-IN` drops
every guest-originated packet to the host and there is no default route. An
exec channel is `host -> guest`, which the containment chain has always
allowed (its `ESTABLISHED,RELATED -> RETURN` rule is what carries the replies).
The guest gained no reach; labhost gained a door. Same shape as `beos` and
`w2kalpha`.

Three things make it work, all on the guest's DISK and therefore all inside the
golden — arm and re-verify them with
[`streamhost/guest-agents/aix432/enable-telnet-exec.py`](../../streamhost/guest-agents/aix432/enable-telnet-exec.py),
which is idempotent and ends in a real end-to-end call:

1. **One line back into `/etc/inetd.conf`.** The retronet bring-up stripped it
   to the three CDE services; `inetd` was running the whole time with nothing
   on 23. The line restored is `/etc/inetd.conf.preretronet`'s own, byte for
   byte. Then `refresh -s inetd`.
2. **`chuser rlogin=true root`.** AIX ships root with `rlogin = false`, so
   telnetd answers a *correct* password with `3004-306 Remote logins are not
   allowed for this account`. Budget an hour for this if you skip it: it reads
   exactly like a wrong password.
3. **`exec_subshell: true`** in the registry, which makes the shared client
   wrap the command in `( … )`. AIX's ksh IS the login shell, so a bare
   `exit N` would end the session and surface as a channel *fault* rather than
   as rc N.

The password is never in the registry: the launcher republishes it from the
gitignored `registry/local.env` (`RN_AIX432_EXEC_PASS`) into
`<station dir>/telnet-exec.passwd`, mode 0600, on every start — the same rule
and shape as beos' `telnet-exec.passwd` and rhapsody's `serial-exec.passwd`.

**Not the serial line, and this is worth knowing before you try.** The station
has exactly one serial port (`sa1` / `tty0`) and the golden already holds a
live root `ksh` on it — which is the **parent of the CDE Netscape the exhibit
shows**. Putting a getty there (`chdev -l tty0 -a login=enable` +
`mkitab`) makes init and that shell fight over the port: `INIT: Command is
respawning too rapidly`, and the only way to win the fight is to kill Netscape.
The serial line keeps its one job — it is the **bootstrap** the enabler script
drives, and the fallback if the retronet tap is ever down.

## Golden, input, and rollback

- Reset mode: `loadvm golden` — declared in the registry, **not yet baked**. The
  golden is being captured by a parallel bring-up; a checkpoint, its binary and
  its device set are ONE combination, so it is only trustworthy once the tracked
  launcher exists and the NIC question is settled.
- Pointer and keyboard: **PASS**. Motion converges to ±1 px against the cursor
  registers and a click actuates on the framebuffer (Netscape's Back button
  repaints the page); the keyboard rides the ordinary QEMU/dbus path, which the
  PS/2 set-3 fix is what bought.
- Cold boot: **not audited.** `scripts/coldboot/aix432-bootrec-arm.sh` is still
  the scaffold's draft case arm with a `TODO` disk list; no boot clip.
- Credentials reference only, never values: `guest/aix432`.
- Rollback: nothing is deployed, so the rollback is deleting the sandbox disks.
  The install is reproducible from the recipe above, at the cost of the ~60 min
  TCG BOS install plus the fork build.

## What still gates promotion

1. **A tracked launcher.** `streamhost/stations/aix432/` does not exist. Until
   it does, `runtime.qemu.launcher` / `envFixture` / `emitArgs` / `auxFiles` are
   deliberately absent from the registry entry rather than pointing at files
   nobody has written, and `launcherParity.status` is `unwritten`.
2. **A restore-proven golden**, baked against that launcher's pinned device set
   — with the NIC decided first.
3. **A public-relay-reachable port.** UDP **54201 is outside**
   `ports.publicRelayLow..High` (54080-54200) in
   [`registry/registry-v1.json`](../../registry/registry-v1.json). Promoting the
   entry to `production` as it stands **fails validation**, and shipping it past
   that check would put an exhibit on the floor that streams perfectly on the
   LAN and is unreachable through the edge. Slot 201 was chosen because slots
   **152-200 are reserved for the walk-in clone pool**
   ([`WALKIN-BRIEF.md`](../lab/WALKIN-BRIEF.md)) — the scaffolder's allocator
   does not know about that reservation. Either widen the relay window (edge
   nftables, the `wg0.conf` comment, `docs/PUBLIC-GALLERY.md` and
   `publicRelayHigh` together) or take a slot inside it.
5. The usual lineup work the playbook lists for any new station — poster prose
   and hero image, `spa/src/scene/machines.ts` + `machineIdentity.ts` +
   `keyboardProfiles.ts` — and **three** runtime documents published, not two.
   The third is `golden-manifest.json`, whose keys are the allow-list for
   `POST /restore/<id>`: miss it and the tile looks perfectly healthy while its
   "reset to golden" button returns `404 unknown osId`. It is no longer a file
   anyone maintains by hand — it is **rendered from this registry entry**
   (production `id` + `reset`, ordered by `render.goldenOrder`) and published to
   `/data/vms/streamhost/serve/golden-manifest.json`, so the trap now reduces to
   remembering to publish after regenerating. `tiles.json` and
   `gallery-manifest.json` are the other two.
