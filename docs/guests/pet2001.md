# Commodore PET 2001 (1977) — gallery tile notes (udp/54088)

**Guest:** a captured **Debian 13 (trixie) x86_64 kiosk** running **VICE `xpet -model
2001`**, emulating the **original 1977 Commodore PET 2001** at its untouched
cold power-on screen. An **"emulator bridge"** tile — streamhost captures the
Linux framebuffer + AC97 audio exactly like every other tile. See
**`streamhost/docs/BRIDGE.md`**.

**Shared base:** `/data/vms/bridge/bridge-base-trixie.qcow2` — already contains the
whole VICE family and its ROM tree.
**Build script (tile):** `scripts/build-guests/tiles/pet2001.sh` — thin overlay +
kiosk `launch.sh` + ROM repair + quiet console + golden bake + a two-step
framebuffer proof of the type-in demo, fully automated, ~2 minutes.
**Tile dir (host):** `/data/vms/streamhost/tiles/pet2001/`.
**Registry entry:** `registry/tiles/pet2001.json` (slot 88, udp 54088, VMID 224,
ssh hostfwd 127.0.0.1:5824).

**This is the oldest machine in the gallery.** Its `era_year` of 1977 is the new
floor: the previous floor was 1980 (`vic20` and `plus4`), and the `apple2` tile
is registered as a **1988** Apple IIe running GEOS, not a 1977 Apple II.

## Media and license — there is none to stage

VICE bundles the Commodore ROMs, which for the PET means the whole family's
BASIC/KERNAL/editor/character sets. The 1977 machine needs no tape, no disk and
no cartridge, so this tile has **no external media, no licensed image and no
`check-assets.sh` row**.

- **VICE 3.9** — GPLv2; bundles the PET ROMs for emulation use.

### Which model, and how we know it is the right one

`xpet -help` offers `2001/3008/3016/3032/3032B/4016/4032/4032B/8032/8096/8296/
SuperPET`. `-model 2001` is the 1977 original, and VICE's own `-dumpconfig`
proves it is a real machine configuration rather than a badge:

| Resource | Value | Meaning |
|---|---|---|
| `RamSize` | `8` | the 8 KB PET 2001-8 |
| `Crtc` | `0` | **no 6545 CRTC** — the 1977 machine generated video with discrete logic; every later PET used the CRTC |
| `VideoSize` | `40` | 40 columns |
| `KeyboardType` | `4` | the chiclet **graphics** keyboard, not the later business layout |
| `CrtcPaletteFile` | `2001-blueish.vpl` | the original's blue-white phosphor |

ROM set 1 (`rom1g.vrs`) selects `basic-1.901439-09-05-02-06.bin`,
`kernal-1.901439-04-07.bin`, `edit-1-n.901439-03.bin` and
`characters-1.901447-08.bin`. The sibling tile `cbm8032` is the other end of the
same family — 80 columns, business keyboard, BASIC 4 — and is deliberately a
different exhibit.

## The fixture, and how a visitor drives it

The golden is **the machine's own untouched cold power-on screen**:

```
*** COMMODORE BASIC ***
 7167 BYTES FREE
READY.
```

blue-white on black, with the block cursor beneath it. Nothing is curated,
nothing is typed before the bake, and nothing is sent after the restore. This is
the whole user interface a PET had, and it is the state the machine chose for
itself — the lesson the `plus4` tile learned the hard way when its first golden
rested deep inside an application and dropped visitors into the middle of a
spreadsheet with no idea how to leave.

The interaction lives in the SPA, around the honest idle screen: a **type-in
demo** (`spa.demoProgram`) of four lines of PET BASIC.

```basic
10 print chr$(147)
20 x=int(rnd(1)*1000)
30 poke 32768+x,81
40 goto 20
run
```

It is period-correct in the strictest sense: the PET had **no graphics mode at
all**, so everything anyone drew on one was done by poking character codes into
screen memory at `$8000` = 32768. Screen code 81 is the filled circle; the
screen fills with them in a few seconds. `CHR$(147)` is the PETSCII clear-screen
control code.

### The keyboard is not laid out like a PC's

Two things matter and both are declared in the registry:

- **Letters are upper case unshifted; SHIFT gives the graphics set.** That is
  the reverse of every modern keyboard, so the entry declares
  `keyboard.letterCase: "upper-only"` and the SPA typist sends letters
  unshifted. Sending `Shift+A` would poke a graphics character into the listing.
- **`spa.demoProgram.perCharMs` is 180.** `validate_demo_pacing` in
  `scripts/tiles-registry.py` requires it to be at least the tile's drain rate,
  `SH_KEY_MIN_HOLD_MS + SH_KEY_MIN_GAP_MS` = 160 ms; the SPA's default of 70
  would out-run the guest and fail the gate.

Everything else — `$ ( ) * + ,` and the digits — arrives correctly through
VICE's default SDL symbolic keymap for the graphics keyboard
(`sdl_grus_sym.vkm`), which is why no `SH_KEY_MAP` is declared. That was proven
by typing the whole listing and reading it back with `LIST`, not assumed.

### Special keys: one verified, one not

The demo is an **infinite loop**, so a stop key is not a nicety — without one a
visitor who runs it can only get back to `READY.` by resetting the tile. Both
candidates were tried on the live tile and only one works:

| Key | Host key | Result |
|---|---|---|
| **RUN/STOP** | `Esc` | **VERIFIED** — breaks the running demo: `BREAK IN 30` / `READY.` (`keyboard-3-runstop.png`) |
| INST/DEL | `Backspace` | **DOES NOT WORK** — `PRINT 1234` survived two presses unchanged (`keyboard-4-del.png`) |

So the proposed OSK profile ships RUN/STOP and omits ⌫, following the rule at
the top of `keyboardProfiles.ts`: a key whose end-to-end guest mapping is
unverified is deliberately absent, because a dead key is silent through the
whole pipeline. The PET 2001 has no Commodore key, no RESTORE and no function
keys, so the c64 profile is the wrong one to reuse.

## Device set and launcher

Identical in shape to its bridge siblings (`c64`, `vic20`, `plus4`, `apple2`,
`atarist`, `amiga`, `mpf2`) — see `streamhost/tiles/pet2001/qemu-streamhost.sh`,
which is the device-set ledger. The kiosk launcher is:

```
xpet -sounddev alsa -model 2001 -CRTCdsize
```

on an **800×600 X root**.

**Window vs X root, measured here (2026-08-09).** There is no window manager, so
an SDL window larger than the X root is silently clipped and mispositioned.
Recon had recorded a PET clipped at 1024×768 — but that was the 80-column 8032.
Measured with `xwininfo` on this overlay, the 40-column 2001 at `-CRTCdsize` is
a fixed **768×532** window:

| X root | Window placement | Result |
|---|---|---|
| 1024×768 (base default) | `+128+118` | not clipped, but only ~52% of the captured frame carries picture |
| **800×600** | `+16+34` | not clipped, ~85% of the frame — **shipped** |

Dropping `-CRTCdsize` instead would halve the picture to 384×266 and is strictly
worse. Real SDL fullscreen is not an option: it renders BLACK under std-VGA
capture (see `scripts/build-guests/tiles/amstradcpc.sh`).

As for every VICE tile, **the kiosk profile must not redirect `startx`'s output
to a file**: VICE 3.9 segfaults in `vice_banner()` whenever stdout is not a
terminal and prints nothing at all — backtrace and symptom in
[`vic20.md`](vic20.md). `pet2001.sh` also repairs the PET data set from the
retained source tree and asserts the four ROMs model 2001 loads **plus
`rom1g.vrs` and `2001-blueish.vpl`** — the palette is not a `.bin`, so a
`*.bin`-only repair would miss it. On this box the PET `.bin` set happened to be
complete already; the assertion stays because `make install` silently skipping
data files is what killed the c64 and vic20 builds.

## Keyboard pacing

`SH_KEY_MIN_HOLD_MS=80`, `SH_KEY_MIN_GAP_MS=80` — four frames each way.
**Carried over from the VIC-20's bisect rather than re-measured**: same
emulator, same host, and the failure those numbers guard against is a host
scheduling stall rather than a property of the emulated machine (40/40 corrupted
1 line in 22; 80/80 none in 22 — see [`vic20.md`](vic20.md)). The two-frame
figure derived from a frame period is a **floor, not an answer**. The build's
own type-in proof is typed at exactly 80/80, so the proof exercises the shipped
pacing. Re-bisect with `scripts/dev/emu-key-pacing-bisect.py` if this tile ever
drops characters.

## Archetype and 3D placement

The scaffold's `beige-tower-crt` is wrong for a 1977 all-in-one: the PET is a
sheet-metal trapezoid with an integrated 9-inch monochrome CRT, a chiclet
keyboard and a cassette deck, and there is no tower anywhere in the picture.
None of the seven `ArchetypeId` values describes it exactly; the closest honest
one is **`mono-terminal`** ("monochrome Bell-Labs/DEC terminal"), which at least
gets the two things that matter — monochrome, and one integrated object. The
field is now essentially a label (the SPA uses it only to detect `touch-phone`
and to validate the manifest), and the real appearance comes from
`spa/src/scene/machines.ts`, where the proposed assembly is
`{ kind: 'terminal', body: 'terminalC' }`: the one existing all-in-one body with
its own tilted integrated screen and no separate monitor or keyboard, and
otherwise unused, so it does not duplicate another exhibit's silhouette.

A bespoke archetype/body would need: the trapezoidal sheet-metal wedge, the
recessed 9-inch screen set well back from the front edge, the calculator-style
chiclet keyboard **with its own numeric keypad on the right**, and the cassette
door in the front face — the four features that make a PET recognisable at a
glance.

## Memory

Built and shipped at **`-m 768`**. Measured with the kiosk and `xpet` running,
the guest keeps `MemAvailable` at **416 MB** of 725 MB — far above the 200 MB
floor — so there is no case for 1024. Host-side QEMU RSS with the tile live and
streaming is **~707 MB** (`ps -o rss=`), plus ~47 MB for the streamhost daemon.

| `live-service-golden.png` | the frame the **running `streamhost@pet2001` service** is encoding |

The readiness predicate is deliberately falsifiable in two independent ways, and
it had to be: **the first run of this builder baked the wrong screen.** Counting
lit phosphor alone, GRUB's `Booting 'Debian GNU/Linux'` text screen measures
2067 lit pixels — inside the band that the PET's 1600-pixel banner occupies —
and the bake pointed straight at it. What separates them is geometry: VGA text
mode is 720×400 and the kiosk's X root is 800×600. The shipped predicate
requires **both** the exact 800×600 capture size (rejecting every console/GRUB
frame) **and** a lit-pixel count inside 1200…4000 (rejecting a black root, a
dead `xpet`, and any screen carrying typed output).

Measured lit-pixel counts, which are what the assertions compare against:

| Screen | Lit pixels |
|---|---|
| bare X root / dead `xpet` | 0 |
| GRUB text screen (720×400) | 2067 — **rejected on geometry** |
| power-on banner, cursor off / on | 1600 / 1841 |
| program typed and LISTed | 6077 |
| demo running | 10285 → 19360 |

## Cold boot and rollback

Zero input is genuine, and since the golden is the power-on screen itself, a
cold boot and a restore reach the same place. See
`scripts/coldboot/pet2001-zero-input-prep.md`.

To withdraw the tile: `systemctl stop streamhost@pet2001`, set
`enabled: false`, regenerate, republish the three runtime documents (tiles.json, gallery-manifest.json AND golden-manifest.json — the third is the reset allow-list). To rebuild:
`scripts/build-guests/tiles/pet2001.sh --force`, which replaces `overlay.qcow2` and so
**destroys the golden inside it**, then bakes and re-proves a new one.

The tile runs the **canary** streamhost binary
(`/usr/local/lib/streamhost/tiles/pet2001/current`, the same build vic20, plus4
and mpf2 use). The shared fleet binary does **not** implement
`SH_KEY_MIN_HOLD_MS`, so promoting this tile to the fleet build would silently
remove its key pacing.
