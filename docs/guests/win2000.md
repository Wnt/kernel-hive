# Windows 2000 Professional — high-resolution checkpoint

The live `win2000` station ships at **1600x1200, True Color (32 bit)** on QEMU's
`-vga std` device (Bochs VBE, 16 MiB), driven by the **VBEMP** universal VESA
display miniport (bearwindows / AnaPa). Display Properties reports the adapter
as *"VBE Miniport - Standard PCI Graphics Adapter (VGA)"*.

## Display: std VGA + VBEMP at 1600x1200 (era-correct bump, 2026-07-27)

Previously the station ran `-vga cirrus` at 1024x768x16 on the inbox Cirrus 5446
driver (see the superseded record below). Cirrus's fixed 4 MiB VRAM cannot hold
a 1600x1200x32 desktop (7.68 MiB) and QEMU 11 blanks GDI text on Cirrus at
hi-res, so the adapter was swapped to `-vga std` + VBEMP. A display-adapter
change breaks `loadvm golden` matching, so this was an atomic rebuild: a new std
launcher plus a checkpoint recaptured on the std device set.

VBEMP binds to the QEMU stdvga PCI device (`PCI\CC_0300`) and sets real VESA
modes through the Bochs VBE BIOS via the Windows `framebuf` display driver — a
packed-linear framebuffer with a software cursor (so the cursor is now captured
in the stream, unlike the Cirrus HW-cursor path). At 1600x1200x32 the desktop,
window chrome, and anti-aliased text render tear-free, static and during a
window drag (Win2000 defaults to outline-drag, which is ideal for the encoder).

### Two VBEMP gotchas (both required for a stable Win2000 boot)

1. **Use the `VBE20/W2K` build, not `VBE30`** (VBE30 mis-sets the mode) and not
   the `VBE20/XP` build (it does not bind on Windows 2000 — it silently falls
   back to 16-colour 640x480 VGA).
2. **Set a `framebuf`-valid default mode in the inf before install.** The stock
   `vbemppnp.inf` leaves the default mode unset, so on first activation VBEMP
   inherits the prior **640x480x4bpp (16-colour)** VGA mode. `framebuf.dll` does
   not support 4bpp, so `winlogon.exe` faults (`0xc0000005`) and the system
   drops to a `c000021a` STOP. Adding `DefaultSettings.BitsPerPel=16`,
   `XResolution=1024`, `YResolution=768` to `[Vbemp_SoftwareDeviceSettings]`
   makes VBEMP come up at a valid mode; the crash disappears. (`VBE_DDC=0` and
   `VBE_USWC=0` were also set as hardening; they were not the crash cause.)

## Install / capture recipe (clone-proven then live)

1. Boot the checkpoint disk on `-vga std` with a FAT12 floppy carrying the patched
   `VBE20/W2K/PNP/{vbemp.sys,vbemppnp.inf}` + `CPL/vbemp.cpl` (`-fda vbemp.img`).
2. The Found New Hardware Wizard auto-runs for "Video Controller (VGA
   Compatible)": Next → Search → Next (Floppy checked) → Next → found
   `a:\vbemppnp.inf` → Next → Yes (unsigned-driver warning) → Finish.
3. ACPI power off, then cold-boot **without** the floppy (the production device
   set). VBEMP is now active at 1024x768.
4. Display Properties → Settings: Colors → **True Color (32 bit)**, Screen area
   → **1600 by 1200 pixels**; Apply → OK on the pre-switch warning → on "keep
   these settings?" send **Alt+Y** (default is No, reverts in 15 s).
5. Close, verify a clean idle 1600x1200 desktop by real screendump, then
   `savevm golden` on the std device set (floppy absent — the FDC drive must not
   be in the checkpoint device set). Prove `-loadvm golden` restores it.

The floppy is present only during driver install; the captured checkpoint device set
is `std VGA + AC97 + usb-tablet + rtl8139`, no floppy media — matching the
production launcher exactly so `loadvm golden` stays valid.

## Pointer

usb-tablet absolute input covers the full 1600x1200 surface 1:1; the software
cursor is captured. Input-probe calibration corners were rescaled to `a=[300,900]`,
`b=[1200,375]`.

its pidfile-owned QEMU exited, copy both backups over the live files, then start
the service.
