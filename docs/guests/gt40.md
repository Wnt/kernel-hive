## The machine, and the one thing that makes it different

The GT40 is a PDP-11/05 with a **VT11 display processor** in the same cabinet.
The VT11 is not a framebuffer: it reads a *display file* out of core and steers
an electron beam along it, so what is on the glass is a set of lines, not a
raster. Its other half is a **light pen** — a photocell in a barrel on a cord
that reports back the instant the beam passes under it.

**This station takes no keyboard input at all.** The 1973 Lunar Lander uses the pen
for everything: the twelve-item telemetry menu down the right edge, the four
rotation arrows, and the throttle bar you slide the pen along. `lunar.txt`,
which ships beside the tape, documents no key anywhere. So the station emits
`--pointer abs`, carries a `usb-tablet`, sets **no** `SH_KEY_MIN_*` pacing, and
its kiosk keeps the X core cursor (every other kiosk runs `startx
-nocursor`).

In Open SIMH the pen is **mouse button 1 and nothing else**:

```c
/* display/sim_ws.c, ws_poll() */
if ((display_lp_sw = mev.b1_state)) {
    ws_lp_x = mev.x_pos;
    ws_lp_y = (ypixels - 1) - mev.y_pos;
```

The pen is on the glass only *while* the button is held, and its position is the
position carried by that same event. A press **is** the gesture; there is no
hover, and a press with no vector under it simply does nothing. That makes this
the natural home for the gallery's **stylus** path — read
[`docs/lab/INPUT-DEBUGGING.md`](../lab/INPUT-DEBUGGING.md): a stylus on a desktop
exhibit takes the mouse/pen branch, not the touch recognizer.

## Media and license — there is none to stage

`lunar.lda`, the 1973 paper tape itself, ships **inside the Open SIMH tree** at
`PDP11/lunar11/`. Nothing is fetched at build time, nothing is staged under
`/data`, nothing is committed. The build asserts its hash so a moved pin cannot
silently change the exhibit.

- **Open SIMH** — MIT, pinned at commit `a1f57fa3738ed31148d31126ba1a7278ff845c6d`
  (2026-07-03 master; there is no v4 release tag past v4.0-Beta-1).
- **`PDP11/lunar11/lunar.lda`** — 13 824 bytes, sha256
  `95f314570424a2d3a5e5e4684b78d5b5f519d6f16931854540dc736220340930`,
  in-tree with the MIT-licensed simulator. Written for the GT40 in 1973 by
  DEC's Jack Burness.

**Debian's packaged `simh` is 3.8.1 and is built WITHOUT SDL video.** It cannot
draw a VT11 at all. Never use it.

## Building SIMH into the overlay

The frozen bridge seed ships five emulators and SIMH is not one of them, so this
station follows the **`amiga.sh` precedent** and builds Open SIMH **into the station's
writable overlay**. Nothing extra has to be installed: the base already carries
`gcc`, `make`, `git`, `libsdl2-dev`, `libpng-dev` and `libpcre2-dev`, so

```
git clone https://github.com/open-simh/simh.git && cd simh
git checkout a1f57fa3738ed31148d31126ba1a7278ff845c6d
make pdp11 -j2        # 90 s in the guest
```

produces one 2.8 MB `BIN/pdp11` compiled with
`-DUSE_DISPLAY -DHAVE_LIBSDL -DUSE_SIM_VIDEO`. `libpcap-dev` is **optional**
(SIMH falls back to TAP + SLiRP, which is enough for PDP-11 networking) and
`libvdeplug-dev` is **not needed**; neither matters for this station, which has no
emulated network at all.

**A from-scratch NVMe rebuild needs the same steps added to
`scripts/build-guests/lib/bridge-base.sh`** so the base captures SIMH in. That file is
shared and is not edited by this station's work; the exact snippet is in the station's
build report and in the registry notes.

## The SIMH configuration

`/opt/bridge/gt40/gt40.ini`, and every line is load-bearing:

```
set cpu 11/70
set cpu 128K
set dli enable
set dli line=2
set vt enable
set vt crt=vr17
set vt scale=1
set vt hspace=narrow
load /opt/bridge/gt40/lunar.lda
dep 32530 1
run
```

| Line | Why |
|---|---|
| `set cpu 11/70` | a **Unibus** CPU, so the VT device autoconfigures at vector 320. `PDP11/lunar11/README.txt` asks for exactly this. It is not the GT40's own 11/05 — SIMH does not model that combination — and it is the honest deviation to know about. |
| `set dli enable` / `line=2` | the DL11 the VT's vector is derived from |
| `crt=vr17` | the 17-inch tube. **`vr14`, the GT40's own, clips the menu column mid-word** (`ALTITUD`, `FUEL LEF`) — the recon measured it. `vr17` is the tube DEC fitted to the GT42; the CPU, the VT11 and the pen are the GT40's. |
| `hspace=narrow` | the character spacing the 1973 menu was laid out for |
| `dep 32530 1` | `README.txt`'s own trick: the tape spins a counter to time its introductory message, and SIMH counts instructions rather than time, so without this the start "takes forever" |

**Two knobs that do nothing, both already tried.** `set throttle` is useless —
the lander busy-spins, so there is no idle to throttle. `set cpu idle` belongs
in a *terminal* ini (where it takes a simulated shell from 100 % of a core to
2.1 %); this program never idles.

## Geometry

`crt=vr17 scale=1` is a fixed **1024x1024** SDL window that cannot be resized,
so the same rule the other kiosks use applies in reverse: shrink the X
root to the smallest advertised mode that *contains* it. On the kiosk's
bochs-drm that is **1280x1024**, and SDL centres the window at exactly
`+128+0` — verified with `xwininfo`, and asserted by the builder. `1024x768`
and everything below it clips; larger modes only cost encode. The root is
painted black, so the black CRT and the black root read as one screen.

The builder also asserts the **twelve-item menu column** measures ~5450 lit
pixels. That is the assertion that would have caught the `vr14` clipping, and it
is deliberately a *wait* rather than a single sample: on the very first load the
tape draws its introductory message, which has no menu at all, and a one-shot
assertion failed a perfectly healthy build there.

## CPU, memory and idle pause

Measured on labhost, 2026-08-09, inside the 2-vCPU kiosk:

| Configuration | SIMH CPU | Note |
|---|---|---|
| `SDL_RENDER_DRIVER=software` (shipped) | **177 %** of a core | 2 llvmpipe workers, 9 threads |
| no `SDL_RENDER_DRIVER` | 184 % | 2 llvmpipe workers — the difference is inside noise |
| `LP_NUM_THREADS=0` | 193 % | threads gone, work moved onto the emulator thread; **worse** |

The recon's headline (205 % → 118 % from `SDL_RENDER_DRIVER=software`) was
measured on the **host**, where sixteen llvmpipe workers spawn. In a 2-vCPU
guest only two ever do, so the setting is kept because it is correct for a
GPU-less kiosk, not because it buys 1.7x here. The real cost is phosphor-decay
ageing plus a 1-megapixel software blit, and it is inherent.

- **Host QEMU RSS: 758 MB** (`-m 768`).
- **Guest `MemAvailable` with the simulator running: 306–367 MB** — comfortably
  over the 200 MB floor.
- **`SH_IDLE_PAUSE_SECS=60`** is set explicitly, and matters more here than
  anywhere else: this is the one exhibit that never sits still, so without the
  pause it would burn ~1.8 cores with nobody watching. Verified: 60 s after the
  service started with no sessions, `info status` reports `paused` and the host
  QEMU process measures **0 %**.

## The scene

The checkpoint is **the first seconds of a fresh lunar descent** — the LEM in the
upper left with its engine firing, ~18 000 feet, a full tank, the throttle bar
at 75 %, the whole landscape and the whole menu.

Choosing it needed one observation: **the exhibit is self-sustaining.** Over a
300-second unattended run the LEM falls for about two minutes, crashes with
`WELL, YOU CERTAINLY BLEW THAT ONE.  THERE WERE NO SURVIVORS`, holds that for
~12 s and **restarts itself** — a 135 s loop. So the checkpoint can rest on a moving
screen, and the capture rides the program's own loop to a deterministic moment:
wait for the crash message, then for the restart it triggers. A visitor who
presses reset therefore gets a **new game**, not the middle of somebody else's
doomed trajectory.

Two traps were paid for in that predicate and are encoded in the builder:

- The crash message is **not a steady raster**. The VT11's phosphor refresh
  leaves whole frames blank, so "the crash band went quiet" fires *mid-message*
  (measured: a 0 between two 3104s inside one 12 s message). The restart edge
  must require the LEM to be back in its start box in the **same** sample.
- **`loadvm` reverts the disk, not just RAM.** An internal qcow2 snapshot
  carries the disk too, so a re-synced `/etc/bridge/launch.sh` is silently
  reverted by the next `-loadvm golden` boot and the kiosk comes up running the
  old launcher with nothing anywhere saying so. `gt40.sh` therefore **never**
  boots with `-loadvm`; only the production launcher does.

## Driving it

There is no keyboard and no shell inside the simulated machine.
`labctl exec gt40 "<cmd>"` reaches the **Debian kiosk**, not the PDP-11.
`labctl type` / `labctl key` do nothing here.

The pen is driven from the host by `/data/vms/streamhost/tiles/gt40/pen-drive.py`
(written by the builder), which speaks QMP: absolute tablet move, button 1 down,
hold, up — the same path streamhost's `dbus-abs` backend uses.

```
python3 pen-drive.py <qmp.sock> point 1070 901     # the ANGLE menu item
python3 pen-drive.py <qmp.sock> park  8 8          # get the cursor out of the way
python3 pen-drive.py <qmp.sock> burst 20 0.15 1035 755 120 268   # menu blink
```

Root-pixel coordinates on the 1280x1024 kiosk screen; the VT11 window is at
`+128+0`. The four readout slots along the top are at y≈287 (slot 1 at x≈210);
the menu items run from `HEIGHT` at y≈768 to `SECONDS` at y≈1011, x≈1037–1150.

## Verification (2026-08-09)

Evidence in `/data/vms/streamhost/tiles/gt40/evidence/`:

| Artifact | Shows |
|---|---|
| `cold-boot-vectors.png` | the kiosk cold-booting straight into the VT11, before any curation |
| `ready-before-golden.png` | the fresh descent that was captured — the frame reset returns to |
| `golden-restored.png` | `loadvm golden` landing on that same fresh descent |
| `pen-1-angle-selected.png` | after a light-pen touch on `ANGLE` |
| `golden-restored-after-pen.png` | the restore that cleared the selection |
| `live-service-frame.png` | the station mid-descent under `streamhost@gt40` |

**The light-pen proof is the program's own acknowledgement, not "the
framebuffer changed"** — which a falling lander satisfies with no pen at all.
`lunar.txt`: *"the user points the light pen at the item he wishes to display …
the item will then start blinking"*. So the assertion is the blink:

| Phase | Menu-column blink range, 20 samples at 0.15 s |
|---|---|
| pointer parked, nothing selected | **0** |
| after a pen touch on `ANGLE` | **376** |
| after `loadvm golden` | **0** |

Two details cost a build each. The X core cursor is composited into the captured
framebuffer, so leaving it inside the measured rect adds 19–34 px of noise and
once masked a real selection — the pointer is **parked** before every
measurement. And the blink has a low duty cycle (2 dark frames in 20), so an
8-sample window missed it outright.

**Not asserted, deliberately:** the *second* half of the gesture — placing the
selected item into one of the four readout slots along the top. It works; the
recon evidence `pen-c.png` shows `10000 HEIGHT` replaced by `-70 ANGLE`, and it
was reproduced by hand on this station. But it needs the pen to land on a glyph
whose x position depends on the current digit count, and the readouts freeze
during the crash message, so a scripted hit is not reliable enough to gate a
build on.

**Audio.** The AC97 card is in the device set for parity with the other kiosks
and `SH_AUDIO=on`, but **the GT40 is silent** — there is no sound hardware
in a VT11 and the tape makes none. Nothing here proves non-silent audio, because
there is nothing to prove.

## Archetype — no existing one fits

`spa.archetypeId` is **`mono-terminal`, as a deliberate fallback**. No archetype
in `spa/src/three/archetypeRegistry.ts` models a vector CRT with a light pen;
`mono-terminal` is chosen only because it is the single monochrome DEC-style CRT
in the set, and everything else (beige PC, tower, putty LCD, SPARC pizza-box,
phone, Apple all-in-one) is worse on every axis. What it gets wrong is that its
other tenants — 9front, HelenOS — are keyboard-driven glass TTYs, and this
machine has no keyboard at all.

A proper `vector-crt-lightpen` archetype would need: a floor-standing DEC
cabinet with the CRT above it rather than a desk terminal; a **round-cornered,
deeply curved** monochrome tube (a calligraphic display, not a raster one); a
light pen on a coiled cord resting in a clip on the bezel; and **no keyboard
tray** — the GT40's LK40 keyboard is irrelevant to what is on screen, and
drawing one invites a visitor to type at a machine that will not answer.

## Cold boot and rollback

Zero input is genuine and a cold boot reaches the same place the checkpoint holds.
See `scripts/coldboot/gt40-zero-input-prep.md`.

To withdraw the station: `systemctl stop streamhost@gt40`, set `enabled: false`,
regenerate, republish the three runtime documents (tiles.json, gallery-manifest.json AND golden-manifest.json — the third is the reset allow-list). To rebuild:
`scripts/build-guests/tiles/gt40.sh --force`, which replaces `overlay.qcow2` and so
**destroys the checkpoint inside it**, then rebuilds SIMH, captures and re-proves a new
one. Without `--force` the script re-syncs the ini, the launcher and the kiosk
profile and recaptures, which is the right move after any edit to those.
