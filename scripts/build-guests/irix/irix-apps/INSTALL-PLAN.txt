RISKS / WATCH-OUTS
------------------
* Writable CHD + SIGKILL = corruption. Always use the `exit` verb; keep the
  per-stage work.chd.<stage> backups (2 GB each, cheap on this pool).
* `xfs_growfs /` on a 512-byte-block V4 XFS is the one unproven step. Backup
  before it; fallbacks listed in step 2.
* inst prerequisite chains can demand Foundation 1/2 and Overlay 1-3 mid-run —
  all five are staged, hot-swap rather than aborting.
* Some demos are IMPACT/O2/Octane-only and will either be unticked (guide) or
  crash on XL24; treat a crash as expected, not as install failure.
* Emulated PS/2 keyboard is slow (~150 ms holds) and the natkeyboard drops
  characters in some widgets — verify every typed line with a SHOT before
  sending the next one. NEVER infer progress from logs or disk state.
* Disk exhaustion: re-check `df -k /` at every checkpoint. 4.6 GiB free after
  the grow, ~450 MiB of payload, so there is ample margin.
* Perf: everything runs at ~44-75% of a real Indy; `inst` of the demos CD will
  take tens of minutes. Budget hours, not minutes.
* FLEXlm: none of the delta products are licence-gated (the licensed ones —
  compilers, Performer dev — are not part of this plan).

INSPECTING A CHD WITHOUT BOOTING IT (minutes -> seconds)
  cp --reflink=always <golden>.chd <yours>/x.chd     # never open the golden
  chdman extractraw -i x.chd -o x.raw                # ~6 s
  mount -t xfs -o ro,norecovery,nouuid,loop,offset=136314880 x.raw mnt
  (partition 0 = XFS root at LBA 266240. The SGI partition table is 16 x
   {nblks, first_lbn, type} big-endian ints at byte 312 of sector 0.)
  norecovery is mandatory -- IRIX's XFS log is "written in incompatible format"
  for Linux, so a READ-WRITE mount is impossible even after a clean IRIX halt.
  nouuid is mandatory -- every image descends from one install.
  Caveat: norecovery shows the pre-log state, so a file the guest wrote just
  before an unclean MAME exit can read as stale or torn.

THE SESSION MECHANISM (source of truth: /var/X11/xdm/Xsession.dt)
  * toolchest and `fm -b` are started UNCONDITIONALLY -- emptying the session
    file cannot cost you the Toolchest or the desktop icons. (Xsession.dt even
    comments that toolchest sets no WM_COMMAND, so SM would never restore it.)
  * `4Dwm -launch` relaunches only session entries that carry a `command` key.
  * TRAP 1 -- the session file must stay NON-EMPTY. The gate is
      if [ -r $wmsession -a -s $wmsession ]
    and the else branch runs `/usr/sbin/startconsole -iconic`. DELETING
    4Dwmsession gives you an iconified console, not a bare desktop.
  * TRAP 2 -- SG_autoSave is read at 4Dwm STARTUP. Editing the resource and
    logging out in the same session still auto-saves the session, because that
    4Dwm instance still has autoSave=true. The bake needs TWO logins: one to
    install the resource, a second (4Dwm now starts with autoSave=false) to fix
    4Dwmsession and shut down. Verified: after the second login's clean
    shutdown the session file was still the ToolChest-only version.
  * 4Dwmdesks is rewritten by 4Dwm continuously (it also rotates a .bak).
    Not worth fighting -- it records placement only and launches nothing.

POINTER
  * Use `xset m 1/1 0`, NOT `xset m 0 0`. The latter reports acceleration 0/1
    (zero numerator, ambiguous); the former reports 1/1 threshold 0. Measured
    gain is identical, so ship the unambiguous one.
  * /.sgisession is left mode 644 ON PURPOSE: Xsession.dt runs it via /bin/sh
    when readable-but-not-executable, so it needs no shebang.
  * Measured with XTest relmove(200,150) on v3:
